## 0. 概述

### 0.1 产品是什么

> **给 Agent 的每个 Skill 算一个"审计就绪度"，并把提升它就绪度的路径算成价格。**

一句话拆三层：

| 层 | 做什么 | 谁看 | 详细 |
|---|---|---|---|
| **主线：ARS** | 度量"这个 Skill 的输出能不能被第三方复核"，并给出提升方案 | 采购方、合规、技术负责人 | 子 PRD 1 |
| **链路：可信/可审计** | 设计→装配→运行→证据→判定→回执→决策→治理 的八段流水线 | 工程团队 | 子 PRD 2 |
| **仪表：成本与预算** | 给每个改造动作与检查定价（CU），让提升路径可排序 | 技术负责人 | 本册 §7 |

层级关系不是并列：**ARS 是目的，链路是手段，仪表是预算表。**

### 0.2 在 Agent 可信 / 可审计里站在哪

四性模型里，前三性已被占，第四性是空位：

| 性 | 回答 | 谁在做 |
|---|---|---|
| 可观测 | 发生了什么 | OTel / Rail |
| 可追溯 | 怎么一步步来的 | LEDGER / AAT |
| 可问责 | 谁签的字 | 责任链 / 签名 |
| **可验证** | **能不能被判对错** | **空位（本产品）** |

时序上，ARS 横跨**设计期**与**治理期**，中段是数据源。它是唯一能"事前"算的指标——L（可定位率）与 C（可编译率）在写下第一条规则时就有了。

### 0.3 三层结构

```
应用层（被测 Skill）
   ↓ claim + evidence
平台层（openJiuwen：Rail 采集 · Studio 呈现 · 自演进回流）
   ↓ 事件流 + 成本信号
【链路】S0 设计 → S1 装配 → S2 运行 → S3 证据 → S4 判定 → S5 回执 → S6 决策 → S7 治理
   ↓ 五维数据
【主线】ARS 打分 → 扣分项 → 改造方案 → 重测 → 闸门
   ↑
【仪表】CU 定价 · 预算 · 债务 · 曲线
```

### 0.4 成败判据

1. 能给出一个**可复算**的 ARS，并有分项解释（不是黑箱分）；
2. 能给出**改造方案与报价**（"补 12 个定位 + 拆 3 条规则 = 34 CU → 78 分"）；
3. 能在一处**卡住**（发布闸：ARS < 70 不许进生产），且卡得有依据；
4. 分数与方案能一键复现（脚本 + 数据）。

## 1. 背景

### 1.1 90 天，七项工作把"验证输出"铺满了

| 日期 | 工作 | 占了哪段 |
|---|---|---|
| 2026-08-19 | LEDGER | 证据图 |
| 2026-09-01 | Agent Flight Recorder | 防篡改记录 |
| 2026-09-02 | ClaimReceipt | 回执、充分性、覆盖、披露 |
| 2026-09-03/26 | SSEG | 传播、定位、门控 |
| 2026-10-01 | VeriHarness | 检查式验证、技能自改进 |
| 2026-10-01 | Verify Claims, Not Scores | 四态裁决、边界 |
| 2026-10-26 | AAT -09 | 记录格式、pre-execution、decision margin |

**共同点：全部度量"结论的质量"，没有一项度量"审计的可能性"。** 它们都假定检查已存在、验证免费。

### 1.2 三堵墙

1. **付不起**：验证成本没人算过，也没法事先估；
2. **说不清**：跳过验证时，跳过这件事在系统里不可见；
3. **补不上**：有些结论结构上验不了（规则主观、缺定位、缺字段），花钱也没用，且没人度量比例。

### 1.3 结论

不是再造一层验证，而是补一条**反向回路**：把运行期的事后数据，变成设计期的可验证性改进。

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 判据 |
|---|---|---|
| G1 | 度量可验证性 | 五项 ARS 全部可从数据算出，口径公开可复算 |
| G2 | 提升可验证性 | 每个扣分项有动作、有价格、有预期增益 |
| G3 | 把就绪度变成闸门 | 发布闸在 Studio 内可用，ARS<70 拦截 |
| G4 | 让"没验"可归因 | 100% 未验证 claim 带等级 + 原因码 + 预算账 |
| G5 | 会复利 | 语料（失败分类 / fixture / 基线）随使用增长，可展示增量 |
| G6 | 成本可解释 | 每个动作有 CU 报价，误差 ≤25% |

### 2.2 非目标

- ❌ 不做新裁决算法（SSEG / 2610.01348 已占）
- ❌ 不做新回执格式（ClaimReceipt 已占）
- ❌ 不做密码学（AFT/AAT 已商品化，用标准哈希链）
- ❌ 不做选择性披露 / 跨组织交换
- ❌ 不做身份体系、签名运营、透明日志
- ❌ 不声称"通用所有 Skill"（只覆盖证据可锚定者）
- ❌ 不做学习型策略 / RL 调度

## 3. 用户与场景

| 角色 | 痛点 | 在本产品里的动作 |
|---|---|---|
| 合规审核员 | 这条结论能不能签字；没签的为什么 | 看 ARS 分项 + 债务 + 导出凭证 |
| 技术负责人 | 上线要花多少、能买到多少可审计性 | 看改造方案报价、拉曲线、调闸门阈值 |
| Skill 作者 / 平台运营 | 我的 Skill 有多少结论结构上验不了 | 看失败分类、改规则、补 fixture |

### 场景走查（DEMO 主线，2 分 40 秒）

1. 打开 Studio，选中一个 Skill → 跑一次 → 产出 12 条 claim。
2. 面板显示 **ARS 46（D 档）**，五项分解：L 0.42 / C 0.30 / R 0.38 / D 0.60 / F 0.70。
3. 点开"可定位率"→ "12 条里 7 条没有精确行号，补上需 8 CU"。
4. 点"可编译率"→ "10 条规则里 7 条编不出来：4 条是主观判断，2 条缺字段，1 条依赖 LLM"。
5. 点"生成改造方案"→ 排序：补定位 8 CU、拆主观规则 12 CU、加字段 14 CU → 合计 34 CU → 预期 78 分（B 档）。
6. 执行 → 重测 → **78 分** → 发布闸放行；对照曲线：34 CU 换 32 分。
7. 反例：不改造直接发布 → 闸门拦截，并记录 `accept_with_grade` + 原因码。

## 5. 核心概念

| 概念 | 定义 | 归属 |
|---|---|---|
| **ARS** | 0–100 的覆盖率指标，五维加权；**不是正确概率** | 主线 |
| **五维** | L 定位 25 / C 编译 25 / R 复算 20 / D 确定性 15 / F 新鲜度 15 | 主线 |
| **Claim** | 被测 Skill 的一条可判定结论，必须有 locator | 链路 |
| **Check** | 五类可执行检查（recompute / cross_source / line_lookup / rule_replay / human） | 链路 |
| **CU** | `tokens/1000 + latency_ms/1000 + human_min×60` | 仪表 |
| **Debt** | 未兑现的验证义务：unverified / stale / structural | 仪表 |
| **Grade** | 单条结论的保证等级 A/B/C/D（覆盖+新鲜度，非概率） | 仪表 |
| **Loop A/B/C** | 验证回路 / 就绪度回路 / 经济回路 | 全局 |

**红线**：ARS 与 Grade 都不得表述为"置信度 / 正确率"。文案里禁止出现百分比概率。

## 7. 仪表：成本与预算

### 7.1 CU 定价

```
CU = tokens/1000 + latency_ms/1000 + human_min*60
```

权重可配。1 人工分钟 = 60 CU ≈ 6 万 token，让"该问人还是该算"成为可比较的选择。

### 7.2 改造动作的价格表（示例，实际用拟合值）

| 动作 | 影响维 | 典型 CU | 说明 |
|---|---|---|---|
| 补 locator | L | 0.5–1 / 条 | 解析输出定位到行/字段 |
| 拆主观规则 | C | 3–5 / 条 | 把"合理""适当"改成可判谓词 |
| 补字段 | C、R | 2–4 / 条 | 规则缺的 required field |
| 补 fixture | C | 1–2 / 条 | 正/反/边界各一 |
| 重跑验证 | R、F | 1–3 / 条 | 输入变更后重算 |

### 7.3 预算与归因

`accept_with_grade` 必须记录：等级 + 原因码（BUDGET_EXHAUSTED / LOW_SEVERITY / DEFERRED / STRUCTURAL）+ 跳过的动作与价格 + 预算快照。

### 7.4 边际分析

对 5 档预算重复求"最省 CU 达到目标档"，得 `(CU, ARS)` 点列；差分即"再花 1 CU 能买多少分"；低于阈值（0.5 分/CU）标"边际枯竭"。
