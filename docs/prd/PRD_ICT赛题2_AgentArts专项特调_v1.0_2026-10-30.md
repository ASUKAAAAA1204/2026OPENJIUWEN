## 0. 一页结论

### 0.1 一句话

> 把“投研日报的每条结论能不能被合规签字”做成一个多 Agent 协作、MCP 工具编排、知识库接入、可评测、可部署的行业 Agent：每条结论有出处、有裁决、有分数、有闸门。

### 0.2 这次专项特调改了什么

| 维度 | 基线（openJiuwen） | ICT 赛题2 特调 |
|---|---|---|
| 平台 | openJiuwen Rail + Agent Studio | 华为云 AgentArts：Agent 编排 + 知识库 + MCP + 部署 |
| 产品形态 | 开发者治理工具 | 金融行业 Agent 应用 |
| 主叙事 | 给 Skill 算审计就绪度 | 给投研日报的每条结论配“可签字凭证” |
| 主用户 | 发布责任人 / 平台运营 | 合规审核员 / 投研负责人 |
| 多 Agent | 非重点 | 6 Agent 协作是主角 |
| 评测 | ARS 五维 | ARS 五维 + AgentArts 效果评估指标 |
| 范围 | 八段全链路 | 最小闭环：抽取→证据→重算→ARS→闸门→改造 |
| 交付 | Studio 一屏 + CLI | AgentArts 工作台 + 审计包 + 部署 URL + 视频 |
| 不变 | claim 原子对象、ARS 口径、发布闸、抗博弈、边界声明 | 同左 |

### 0.3 三个差异化

1. **不是“金融问答 Agent”**：它不只回答，还给每条结论配证据包、裁决结果和发布闸。
2. **不是“可观测工具”**：可观测记录“发生了什么”，它判定“这条结论能不能被第三方复核”。
3. **不是“再做一个验证器”**：它度量“可验证性”，把提升路径算成改造动作与预算，并在发布前卡住。

### 0.4 三个不主张

1. 不主张“世界第一个语义证据链”——LEDGER、VeriHarness、AAT 已占相关位置；
2. 不主张“对齐任何标准”——只写“记录结构参考 AAT 草案字段语义”；
3. 不主张“通用所有行业/所有文档”——只覆盖“证据可锚定”的数值型与行号型结论。

## 2. 产品定位

### 2.1 一句话定位

> **给投研日报的每条结论配一张“能签字的凭证”**：依据在哪、缺什么、能不能复算、发布前该不该拦。

### 2.2 用户与痛点

| 角色 | 痛点 | 在本产品里的动作 |
|---|---|---|
| **合规审核员（主）** | 20 条结论只有 PDF/Word，逐条回源要 2–3 小时；签了怕担责，不签怕耽误发送 | 看 ARS 分项、证据抽屉、发布闸；3 分钟内决定“签/补/拦” |
| 投研负责人 | 不知道日报里哪些结论“结构上不可复核” | 看失败分类与改造方案；决定先改规则还是先发 |
| 技术负责人 | 上线/发布前要补什么、补多少，说不清 | 看改造报价与预测分数；决定预算与排期 |
| 审计/风控 | 事后追责缺证据，无法证明“当时为什么发” | 导出审计包；改一字节即断链，可验证 |
| Agent 运维 | 多 Agent 跑完只看到最终文本，不知道哪一步出错 | 看 Agent handoff、MCP 调用、失败原因码 |

### 2.3 现有做法 vs 本产品

| 现有做法 | 问题 | 本产品 |
|---|---|---|
| 人工逐条核对 PDF/Excel | 慢、漏、不可复现 | 自动回源 + 重算 + 证据包 |
| 只看“日报生成成功” | 成功 ≠ 可审计 | 看 ARS 与五维分项 |
| 有日志但没有判定 | 日志不等于能复核 | 每条 claim 有 verified/refuted/indeterminate |
| 出问题后补记录 | 事后记录不可信 | 记录先于动作；哈希链可校验 |
| 上线只看跑分 | 跑分不解释可审计性 | 发布闸 ARS≥70，未达标拦截并报价 |

### 2.4 价值主张

| 层 | 价值 | 可量化口径 |
|---|---|---|
| 业务 | 合规签字从 2–3 小时降到 3 分钟；发布风险前置 | 单日 20 条结论；签字时间对比 |
| 技术 | 每条结论可回源、可重算、可导出；失败有原因码 | locator 回源率 ≥85%；注入错误 100% 被抓 |
| 商业 | 按“审计次数/发布版本”计价；减少返工与审计工时 | 单次审计成本 ≤6 CU/claim；返工人日下降 |
| 生态 | 在 AgentArts 上可复制到医疗、制造、政务等“证据可锚定”场景 | 替换知识库与规则集，Agent 架构不变 |

### 2.5 非目标

- 不做投研建议生成（本产品审计已有日报，不替代投研判断）；
- 不做交易执行、不做行情预测；
- 不做通用文档问答；
- 不做“全自动签字”——最终签字仍由人；
- 不做跨机构数据交换与签名运营。

## 3. 场景与用户

### 3.1 主场景：投研日报合规审计

**时间**：每个交易日 08:30，投研 Agent 生成持仓日报，含 20 条结论（PE/PB 比较、行业均值、仓位提示、风险提示）。

**现状**：日报以 PDF/Word 发出；合规审核员人工抽查 2–3 条，剩余靠信任；出了问题无法回溯“当时依据哪份数据、哪条规则”。

**目标**：对外发送前，合规审核员在 3 分钟内完成：
1. 哪些结论可签（verified + 证据充分）；
2. 哪些必须补（缺 locator / 缺字段 / 规则主观）；
3. 哪些必须拦（refuted 或 ARS 低于阈值）；
4. 豁免谁、为什么、有效期到哪天。

### 3.2 角色与权限

| 角色 | 权限 |
|---|---|
| 合规审核员 | 查看审计工作台、证据、ARS；执行放行/拦截/豁免；导出审计包 |
| 投研负责人 | 查看失败分类与改造方案；批准规则改造 |
| 技术负责人 | 配置闸门阈值；查看 MCP/Agent 运行指标 |
| 审计/风控 | 只读；下载审计包；离线 verify |
| Agent 运维 | 查看 Agent handoff、工具调用、失败原因；重跑 |

### 3.3 端到端用户旅程

```
导入日报 + 行情/行业均值数据
      ↓
选择“投研日报合规审计”Agent，点击运行
      ↓
IntakeAgent 识别数据画像 / 规则版本
      ↓
ClaimAgent 抽取 20 条 claim + locator 候选
      ↓
EvidenceAgent 回源解析 → 证据包（精确/半精确/无）
      ↓
AuditAgent 真重算 + 行号复核 → 8 verified / 3 refuted / 9 indeterminate
      ↓
ARS 打分（C 3/10 先出 → 设计预警；L 9/20·R 8/20·D 6/10·F 15/20）→ 47 分（D 档）
      ↓
GateAgent 发布闸：ARS < 70 → 拦截 + 改造方案（34 CU）
      ↓
合规审核员选择：执行改造 / 带豁免发布 / 退回
      ↓
改造后重测 → 79 分（B 档）→ 放行
      ↓
导出审计包 → 离线 verify → 归档
```

### 3.4 适配与不适配

| 适配 | 不适配 |
|---|---|
| 数值型 claim（PE/PB、行业均值、仓位比例） | “建议买入”“看好后市”等不可判命题 |
| 证据可回源到文件行/字段 | 依赖未公开/内幕数据 |
| 日频/周频重复运行 | 一次性报告（F 项无意义） |
| 规则成文、有判定条款 | 纯创意生成、无判定规则的文本 |
| 有明确签字人/发布动作 | 没有发布节奏的团队 |

### 3.5 行业可替换性

本 PRD 以金融投研为主场景；架构不变，替换以下三样即可迁移：

| 行业 | 知识库 | 规则集 | 证据形态 |
|---|---|---|---|
| 医疗 | 诊疗指南、药品说明书、病历模板 | 适应证/禁忌证/剂量规则 | 页/段/字段 |
| 制造 | 工艺规范、质检标准、设备手册 | 公差/抽检/安全规则 | 表格/图纸字段 |
| 政务 | 政策文件、办事指南、材料清单 | 材料完整性/时限规则 | 条款/页 |

**迁移条件**：结论必须可锚定到证据；否则输出 N/A，不硬打分。

### 4.2 多 Agent 设计

| Agent | 职责 | 输入 | 输出 | 关键工具 | 失败/降级 |
|---|---|---|---|---|---|
| **IntakeAgent** | 识别报告、数据画像、规则版本；生成 run_context | 日报文件、数据文件、用户选择 | `run_context`（skill/model/data_profile） | 知识库（优先 AgentArts 原生） | 文件缺失 → 提示上传；不猜测 |
| **ClaimAgent** | 抽取 claim + locator 候选 | 日报文本、表格 | `claims[]`（statement / locator / type） | LLM + 知识库 | 抽不出 → `NO_LOCATOR`，不丢弃 |
| **EvidenceAgent** | 回源、解析 locator、构建证据包 | claims、数据源 | `evidence_bundle[]` | `resolve_locator`、知识库 | NOT_FOUND / VALUE_MISMATCH → 记债务 |
| **AuditAgent** | 真重算 + 行号复核 + ARS 打分 | bundles、规则集 | `check_results[]`、`ars` | `recompute_claim`、`score_ars` | 无表达式/超时 → `indeterminate` |
| **GateAgent** | 发布闸/预算约束；生成改造方案；记录豁免 | ARS、债务、预算 | `decision`（release/block/accept_with_grade） | `generate_plan`、`record_waiver` | 闸门不可用 → 降级为报告节点，明确标注 |
| **ReportAgent** | 生成审计摘要与审计包 | 全部状态 | `audit.json`、`audit.html`、`verify` 结果 | `verify_bundle`、`export_bundle` | 导出失败 → 仅 JSON，明确提示 |

**协作规则**：
- 主链串行：Intake → Claim → Evidence → Audit → Gate → Report；
- EvidenceAgent 内部并行：最多 4 个 locator 同时解析；
- handoff 使用固定 schema，不传自然语言大段上下文；
- 共享状态只读快照 + 事件追加，不允许 Agent 互改；
- GateAgent 的人工豁免必须 `human-in-the-loop`，不可自动豁免；
- 任何 Agent 失败都产出 `reason_code`，不静默跳过。

### 4.3 MCP 工具清单

| 工具 | 作用 | 输入 | 输出 | 优先级 |
|---|---|---|---|---|
| `resolve_locator` | 回源解析 locator | locator、source_ref | `RESOLVED / NOT_FOUND / VALUE_MISMATCH` + 实际值 | P0 |
| `recompute_claim` | 真重算 | claim、表达式 IR、操作数 | `verified / refuted / indeterminate` + 证据引用 | P0 |
| `score_ars` | 五维打分 | claims、rules、bundles、checks | `{score, band, dims, n_claims, warnings}` | P0 |
| `generate_plan` | 改造方案 | 扣分项、动作库、CU 单价 | 动作列表 + 总价 + 预测分 | P0 |
| `verify_bundle` | 哈希链校验 | audit.json | `PASS/FAIL` + 首个断链位置 | P0 |
| `export_bundle` | 导出审计包 | 全部状态 | JSON + HTML（可选 PDF 延后） | P0 |
| `query_knowledge` | 知识检索 | query、filter（行业/期间/来源） | top-k 片段 + 元数据 + 版本 | P1 |
| `record_waiver` | 记录豁免 | 谁、何时、理由、有效期 | waiver_id | P1 |

**知识库优先用 AgentArts 原生能力**：`query_knowledge` 是可选封装；若平台原生知识库已能返回来源/元数据，则不重复造 MCP。自定义 MCP 的价值集中在“回源解析、重算、打分、闸门、审计包”这五件事。

**工具纪律**：
- 所有工具幂等；同一输入重复调用结果一致；
- 工具返回必须带 `source_ref` 与 `captured_at`，否则不计入证据；
- 超时统一返回 `indeterminate + TIMEOUT`，不重试到死；
- 不在工具里写业务判断；判断在 AuditAgent/ARS 里做。

### 4.4 知识库设计

### 5.2 P0 功能说明

#### FR-1 Claim 抽取

- 输入：日报文本/表格、数据画像；
- 输出：`claims[]`，字段 `{id, statement, type, locator_candidate, source_hint}`；
- 规则：只抽“可判定结论”；建议性表述标 `SUBJECTIVE`，不进入 ARS 的 L 分子；
- 成本：单 claim ≤1 次 LLM 调用；温度 0；结果缓存；
- 验收：20 条 demo claim 全抽出；每条有 locator 候选或 `NO_LOCATOR`。

#### FR-2 证据包

- 字段：`id, skill, claim, evidence[], checks[], adjudication, integrity`；
- 证据：`kind, ref, locator, digest, captured_at, freshness`；
- 最小集：删除任一条后复算失败，才算最小充分集；
- 验收：每条 claim 可导出；删除测试通过；digest 用 JCS 规范化后 SHA-256。

#### FR-3 LocatorResolver

```
resolve(locator, source) -> RESOLVED | NOT_FOUND | VALUE_MISMATCH
```

- 打开源文件/数据，定位到 `row / line / field`；
- 比对声明值与实际值（数值容差 1e-6；字符串去空白/大小写）；
- 只有 `RESOLVED` 计入 L 的分子；
- `NOT_FOUND` / `VALUE_MISMATCH` 分别记债务原因码；
- 验收：3 类样本分类 100%。

#### FR-4 真重算

- 规则编译为表达式 IR：`const / field / cmp / arith / agg / bool`；
- 从证据读入操作数 → 求值 → 与 claim 数值比对；
- 编译不出 → `indeterminate + NO_EXPR`；
- 边界：除零、空集、单位不一致 → `indeterminate`；
- 验收：10 条数值 claim，注入 3 个错误值全部 refuted；无表达式正确 indeterminate。

#### FR-5 ARS 打分

```
ARS = (0.25L + 0.25C) + (0.20R + 0.15D + 0.15F)
```

| 维 | 定义 | 权重 | 段 |
|---|---|---|---|
| L | 回源解析成功的 locator / 总 claim | 25 | 设计态 |
| C | 编译通过且 fixture 三绿 / 总规则 | 25 | 设计态 |
| R | 独立 verifier 重算一致 / 总 claim | 20 | 运行态 |
| D | fixture 通过的确定性检查 / 总检查 | 15 | 运行态 |
| F | 全部证据 fresh 的 claim / 总 claim | 15 | 运行态 |

- 分档：A ≥85；B 70–84；C 50–69；D <50；
- 样本 <10 或任一维 N/A → `PARTIAL`，只报分项，不出总分；
- 报告标题必须带三元组：`skill@version · model · data_profile`；
- 验收：独立脚本复算差异 = 0；PARTIAL 100% 正确。

#### FR-6 发布闸

| 闸 | 位置 | 规则 | 输出 |
|---|---|---|---|
| 设计预警 | 规则编译后 | C < 0.5 → 低分提示，`design_ack` 确认继续（不阻断） | 失败分类 |
| 发布闸 | 审计后 | ARS < 70 → 阻断 | 阻断 + 改造方案 |
| 预算闸 | 审计后 | 预算耗尽 | `accept_with_grade` + 原因码 |

- 允许人工豁免，但必须记录 `waiver`（谁、何时、理由、有效期）；
- 验收：6 个版本 6/6 正确；漏拦 0；豁免可查。

#### FR-7 改造方案

- 动作库：`add_locator / rewrite_rule / add_field / rerun_check / rerun_stale`；
- 每动作带 CU 与预期增益；按“分/CU”贪心排序；
- 输出：当前分、目标档、动作列表、总价、预测分；
- 验收：47→79 闭环；预测兑现率 ≥70%；CU 偏差 ≤25%。

#### FR-8 审计工作台

一屏包含：
1. 顶部：`skill@version · model · data_profile` + ARS + 档位；
2. 五维条：L/C/R/D/F + 数字；
3. claim 表：状态（verified/refuted/indeterminate/N-A）、证据数、债务原因；
4. 证据抽屉：3 次点击到 `source_ref`；
5. 闸门：放行/拦截/豁免按钮；
6. 改造方案：动作 + CU + 预测分；
7. 审计包：导出 + verify。

验收：3 次点击到证据；拦截那一下可现场演示。

#### FR-9 审计包导出/verify

- `audit.json`：claim、evidence、checks、ARS、债务、豁免、rubric hash；
- `audit.html`：人读版（可打印）；
- `verify`：PASS/FAIL + 首个断链位置；
- 验收：改一字节 → FAIL 且定位到条目。

## 6. 评分与效果评估

### 6.1 ARS 口径

- ARS 是覆盖率指标，不是正确概率；
- 五项全部由计数算出，不由 LLM 直接打分；
- 分数坐标：`ARS = f(skill_version, model, data_profile)`；
- 设计态**只算 C**（跑之前出，作设计预警）；运行态 L+R+D+F（跑完之后出，进发布闸）；
- 样本不足输出 PARTIAL；
- 独立 verifier：demo 20 条全量复算，生产 10% 抽样，差异 ≤5% 才允许发布；
- Demo 中的 47/79 为叙事锚点；所有分项在报告中必须带分母与样本量，最终以 `score_ars` 输出为准。

### 6.2 AgentArts 效果评估指标

| 指标 | 定义 | 目标 | 测量方法 |
|---|---|---|---|
| 场景任务成功率 | 20 条 claim 全抽取；10 条规则全判定 | 100% | Demo fixture |
| Agent handoff 成功率 | 6 个 Agent 交接无 schema 错误 | 100% | 运行日志 |
| MCP 工具成功率 | 工具调用成功 / 总调用 | ≥95% | 工具日志 |
| 知识检索命中率 | top-3 含正确来源 | ≥90% | 20 条查询人工核 |
| 端到端时延 | 20 条 claim 从运行到出分 | ≤8s | 计时 |
| 200 claim 时延 | p95 | ≤20s | 压测 |
| 单 claim 成本 | tokens + latency + human | ≤6 CU | 账单/日志 |
| locator 回源率 | RESOLVED / 总 claim | ≥85% | 人工抽 50 条 |
| 复算一致率 | 独立 verifier 一致 / 抽样 | ≥95% | 独立脚本 |
| 错误召回 | 注入 3 个错误值被 refuted | 100% | 注入测试 |
| 误报率 | verified 中人工判错比例 | ≤10% | 50 条人工复核 |
| 人工采纳率 | 合规审核员接受 verified 结论 | ≥80% | 小样本测试 |
| 闸门准确率 | 应拦/应放 6 个版本 | 6/6 | 混淆矩阵 |
| 审计包防篡改 | 改一字节失败 | 100% | 现场演示 |

### 6.3 测试设计

| 测试 | 样本 | 通过线 |
|---|---|---|
| Locator 三态 | 存在一致 / 不存在 / 值不符，各 5 条 | 分类 100% |
| 重算错误注入 | 10 条数值 claim，注入 3 个错误值 | 3/3 refuted |
| D/F 方差 | 同一数据跑两次，构造 0.5–0.9 区间 | 不再恒为 1.0 |
| 抗博弈 | 10 个形式合规 Skill | ≥8 个被标记 |
| 效度 | 20 条历史争议结论 | 低分档被问倒率 ≥高分档 1.5 倍 |
| 闸门 | 6 个待发布版本，3 应拦 3 应放 | 6/6 正确 |
| 审计包 | 改一字节 | 100% FAIL |

### 6.4 抗博弈

| 机制 | 做法 | 指标 |
|---|---|---|
| held-out | 20 条 claim 不展示给规则作者，只在评分时用 | 与上报分差 ≤10 |
| 抽查 | 10% locator 人工回源 | 一致率 ≥95% |
| 真实性比率 | `resolved_rate` 与 L 并列 | 差 ≤0.15 |
| gaming 标记 | L 涨但 resolved 不涨 | gaming 数 ≥1 |
| 拆分检测 | 等价琐碎谓词不计 C 增益 | 人工抽检 10 条 |

### 6.5 基线对照

| 方案 | 单 claim 成本 | 可复核性 | 结论 |
|---|---|---|---|
| 不审计 | 0 | 无 | 风险不可见 |
| always verify | 约 12 CU | 高 | 成本高 |
| 本产品 | ≤6 CU | 高（策略化） | 成本减半，关键结论全验 |

## 13. 附录

### A. 术语

| 术语 | 含义 |
|---|---|
| ARS | 审计就绪度，0–100 覆盖率指标，不是正确概率 |
| ARS_d / ARS_r / ARS_g | 设计态（只算 C）/ 运行态（L+R+D+F）/ 治理态（全量重算） |
| Claim | 审计原子对象：一条可判定结论 |
| Evidence Bundle | 证据包：locator、digest、freshness、最小集 |
| CU | 成本单位：`tokens/1000 + latency_ms/1000 + human_min*60` |
| Gate | 发布闸：ARS < 70 拦截；豁免留痕 |
| MCP | Model Context Protocol，工具接入协议 |
| PARTIAL | 样本不足时的输出：只报分项，不出总分 |

### C. 答辩口径（五句）

1. “我们不做金融问答，我们给投研日报的每条结论配一张能签字的凭证。”
2. “别的工具记录调用；我们判定这条结论能不能被第三方复核，并在发布前卡住。”
3. “分数有坐标：`skill@version · model · data_profile`，换了任何一个分数就变了。”
4. “47 分不是判决，是报价单：补 9 个定位、原地改写 4 条规则，34 CU 到 79 分。”
5. “我们不审结论对不对，只审能不能被判对错——这是和所有既有工作划清的一句话。”
