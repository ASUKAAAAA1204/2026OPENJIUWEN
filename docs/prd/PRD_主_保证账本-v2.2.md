## 0\. 概述

### 0.1 产品是什么

> **审计的最小对象是结论，评分的稳定单位是 Skill（带版本、模型、数据画像），能卡住的场景是发布。**

一句话拆四层对象：

|层|审计什么|谁来用|度量方式|
|-|-|-|-|
|**结论（claim）**|这条结论能不能被第三方复核|审核员|单条：有/无 locator、能否复算|
|一次运行（run）|这一次跑得怎么样|工程|D、F 在这一层才有意义|
|**Skill @ 版本**|这个包值不值得上架/采购|平台、采购|ARS 主坐标|
|发布版本（release）|这次发版能不能过|技术负责人|闸门在这层|

**为什么主坐标选 Skill**：因为它可发布、可采购、可上架——审计要绑在一个**可交易的单位**上，否则分数无处落地。结论是原子的，但没人会为一条结论买账；运行是易变的，跑两次分数就变，不能当合同标的。

**评分三元组**：同一个 Skill 换模型、换数据，分数会变——ARS 的真实坐标不是 `f(skill)`，而是：

```
ARS = f(skill_version, model, data_profile)
```

不写这三个，分数不可比。报告里必须写"某 Skill 在某模型、某数据画像下的 ARS"。

产品的三条腿：

|层|做什么|谁看|详细|
|-|-|-|-|
|**主线：ARS**|度量"这个 Skill 的输出能不能被第三方复核"，并给出提升方案|发布责任人、合规、采购|子 PRD 1|
|**链路：可信/可审计**|八段流水线（设计→装配→运行→证据→判定→回执→决策→治理）产证据，不打分|工程团队|子 PRD 2|
|**仪表：成本与预算**|给每个改造动作与检查定价（CU），让提升路径可排序|技术负责人|本册 §7|

层级关系：**ARS 是目的，链路是手段，仪表是预算表。**

### 0.2 在 Agent 可信 / 可审计里站在哪

四性模型里，前三性已被占，第四性是空位：

|性|回答|谁在做|
|-|-|-|
|可观测|发生了什么|OTel / Rail|
|可追溯|怎么一步步来的|LEDGER / AAT|
|可问责|谁签的字|责任链 / 签名|
|**可验证**|**能不能被判对错**|**空位（本产品）**|

七项既有工作（LEDGER / ClaimReceipt / SSEG / VeriHarness / 2610.01348 / AFT / AAT）**全部度量单次输出的质量**，没有一项度量"审计的可能性"——它们都假定检查已存在、验证免费。

### 0.3 时序：两段 ARS 夹着链路，不是串行

```
规则集 ──[ARS_d：只算 C]──► 设计预警（C < 0.5 标低分，不阻断）
                                   │ 确认继续
                                   ▼
                     S2 运行 → S3 证据 → S4 判定 → S5 回执
                                   │
                                   ▼
                     [ARS_r：只算 R、D、F] ──► 发布闸（ARS ≥ 70）
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
                 放行                         改造方案
                                                  │ 改规则
                                                  ▼
                                        回到 ARS_d 重算（ARS_g 治理态）
```

ARS 不是链路的前置步骤，而是**在链的两端各算一次**：

|落点|何时|算哪几项|依赖链路吗|
|---|---|---|---|
|ARS_d 设计态|S0/S1 之后，**跑之前**|C|**不依赖**——C 在规则写下时就能算|
|ARS_r 运行态|S4/S5 之后|L、R、D、F|依赖|
|ARS_g 治理态|改造后重测|全部|依赖（前后对比）|

**反直觉的一点**：设计态只算 C 不需要跑一次就能给出。L 需要 claim 的 locator 回源结果，claim 是 S2 运行产物，因此 L 归运行态；这也是本轮把"设计态 L+C"改成"C 单闸"的原因。

### 0.4 三层结构（修正）

```
应用层（被测 Skill @ version / model / data_profile）
   ↓ claim + evidence
平台层（openJiuwen：Rail 采集 · Studio 呈现 · 自演进回流）
   ↓ 事件流 + 成本信号
【第一段 ARS_d】C（可编译）→ 设计预警
   ↓
【链路】S0 设计 → S1 装配 → S2 运行 → S3 证据 → S4 判定 → S5 回执 → S6 决策 → S7 治理
   ↓
【第二段 ARS_r】L（可定位）· R（可复算）· D（确定性）· F（新鲜度）→ 发布闸
   ↓ 放行 / 阻断 → 改造方案 → 回到 ARS_d 重算（ARS_g）
【仪表】CU 定价 · 预算 · 债务 · 曲线
```

### 0.5 成败判据

1. 能给出一个**可复算**的 ARS，并有分项解释（不是黑箱分）；
2. 能给出**改造方案与报价**（"补 9 个定位 + 原地改写 4 条规则 = 34 CU → 79 分"）；
3. 能在一处**卡住**（发布闸：ARS < 70 不许进生产），且卡得有依据；
4. 分数与方案能一键复现（脚本 + 数据）。

### 1.1 90 天，七项工作把"验证输出"铺满了

|日期|工作|占了哪段|
|-|-|-|
|2026-08-19|LEDGER|证据图|
|2026-09-01|Agent Flight Recorder|防篡改记录|
|2026-09-02|ClaimReceipt|回执、充分性、覆盖、披露|
|2026-09-03/26|SSEG|传播、定位、门控|
|2026-10-01|VeriHarness|检查式验证、技能自改进|
|2026-10-01|Verify Claims, Not Scores|四态裁决、边界|
|2026-10-26|AAT -09|记录格式、pre-execution、decision margin|

**共同点：全部度量"结论的质量"，没有一项度量"审计的可能性"。** 它们都假定检查已存在、验证免费。

### 1.2 三堵墙

1. **付不起**：验证成本没人算过，也没法事先估；
2. **说不清**：跳过验证时，跳过这件事在系统里不可见；
3. **补不上**：有些结论结构上验不了（规则主观、缺定位、缺字段），花钱也没用，且没人度量比例。

### 1.3 结论

不是再造一层验证，而是补一条**反向回路**：把运行期的事后数据，变成设计期的可验证性改进。

## 2\. 目标与非目标

### 2.1 目标

|#|目标|判据|
|-|-|-|
|G1|度量可验证性|五项 ARS 全部可从数据算出，口径公开可复算|
|G2|提升可验证性|每个扣分项有动作、有价格、有预期增益|
|G3|把就绪度变成闸门|发布闸在 Studio 内可用，ARS<70 拦截|
|G4|让"没验"可归因|100% 未验证 claim 带等级 + 原因码 + 预算账|
|G5|会复利|语料（失败分类 / fixture / 基线）随使用增长，可展示增量|
|G6|成本可解释|每个动作有 CU 报价，误差 ≤25%|
|G7|分数可被独立复算|独立 verifier 复算 10%，一致率 ≥95%|
|G8|分数抗博弈|10 个红队样本中 ≥8 个被标记|

### 2.2 非目标

**审计边界（什么都不审）**：
* ❌ 不审模型权重与训练数据（做不到，也不该承诺）
* ❌ 不审人格 / 立场 / 价值观（不是可验证命题）
* ❌ 不审安全攻击面（这是另一条产品线，别混进来）
* ❌ 不审"结论对不对"，只审"能不能被判对错"——全案最容易混淆的一句

**工程边界（不造轮子）**：
* ❌ 不做新裁决算法（SSEG / 2610.01348 已占）
* ❌ 不做新回执格式（ClaimReceipt 已占）
* ❌ 不做密码学（AFT/AAT 已商品化，用标准哈希链）
* ❌ 不做选择性披露 / 跨组织交换
* ❌ 不做身份体系、签名运营、透明日志
* ❌ 不声称"通用所有 Skill"（只覆盖证据可锚定者）
* ❌ 不做学习型策略 / RL 调度

## 3\. 用户与场景

三层用户，32 天主攻第一层：

|层|是谁|他要什么|32 天交付|
|---|---|---|---|
|**发布责任人（主）**|技术负责人 / 合规审核员|这次发版能不能过；不过要补什么、多少钱|✅ 闸门装在他手上|
|平台运营（次）|Hub 的运营|哪些 Skill 该退回改造|半个场景（上架前体检）|
|企业采购（次）|采购 / 法务|三个候选哪个更可审|一页对比截图，不做产品|

**主用户选"发布责任人"的理由**：只有他手上有"卡住"的权力。没有闸门，ARS 就只是一份报告，报告没人看。**产品的说服力来自拦截那一下，不是来自分数本身。**

### 场景走查（DEMO 主线）

严格按 ARS_d → 链路 → ARS_r 时序：

1. **设计态 ARS_d**：选中 Skill，规则集 → 编译判定 → C = 0.30（10 条规则 3 条可编译、7 条编不出来）→ 设计预警低分 → `design_ack` 确认继续
2. **链路运行**：S2 采集 → S3 证据（**20 条 claim**，9 条缺精确定位）→ S4 判定 → S5 回执
3. **运行态 ARS_r**：L 9/20 / R 8/20 / D 6/10 / F 15/20 → 综合 **ARS 47（D 档）**
4. **诊断**：点开五维分解 → L 0.45 缺 9 条精确定位（补定位 6.3 CU）；C 0.30 缺 4 条可编译规则（原地改写 12 CU + 补字段 8 CU）
5. **方案生成**：按"分/CU"贪心排序 → 合计 34 CU → 预期 79 分（B 档）
6. **闸门拦截（产品说服力核心时刻）**：ARS 47 < 70 → **发布闸阻断** → 弹窗展示方案报价
7. **两条分支**：
   - a) 执行方案 → 原地改写 4 条规则 → 重跑 → ARS_g 重算（L 18/20 / C 7/10 / R 16/20 / D 10/14 / F 17/20）→ **ARS 79（B 档）** → 发布闸放行；对照曲线：34 CU 换 32 分
   - b) 不改造 → 带 `accept_with_grade` 豁免发布 → 记录原因码 + 预算快照 + 债务台账

**评分三元组标注**：面板标题栏必须显示 `skill@v1.2.0 · model=gpt-5-mini · data=industry.csv:150行`，不写这三个分数不可比。

## 5\. 核心概念

|概念|定义|归属|
|-|-|-|
|**ARS**|0–100 的覆盖率指标，五维加权；**不是正确概率**；坐标为 `f(skill_version, model, data_profile)`，不写这三个分数不可比|主线|
|**ARS_d / ARS_r / ARS_g**|设计态（只算 C，跑之前就能出）/ 运行态（只算 L、R、D、F，跑之后出）/ 治理态（改造后全量重算）|主线|
|**五维**|L 定位 25 / C 编译 25 / R 复算 20 / D 确定性 15 / F 新鲜度 15；**d 态只算 C，r 态只算 L+R+D+F**|主线|
|**Claim**|审计的**原子对象**——一条可判定结论，必须有 locator；Skill 是评分稳定单位，claim 是审计最小单位|链路|
|**Skill @ 版本**|评分的**稳定可交易单位**；可发布、可采购、可上架|主线|
|**发布版本**|闸门的**拦截单位**；只有在这层卡住才有意义|主线|
|**Check**|五类可执行检查（recompute / cross\_source / line\_lookup / rule\_replay / human）|链路|
|**CU**|`tokens/1000 + latency_ms/1000 + human_min×60`|仪表|
|**Debt**|未兑现的验证义务：unverified / stale / structural|仪表|
|**Grade**|单条结论的保证等级 A/B/C/D（覆盖+新鲜度，非概率）|仪表|
|**Loop A/B/C**|A 验证回路（链路八段产证据）/ B 就绪度回路（ARS_d→链路→ARS_r→闸门→改造→重算）/ C 经济回路（CU→预算→债务→边际）|全局|

**红线**：
1. ARS 与 Grade 都不得表述为"置信度 / 正确率"；文案里禁止出现百分比概率；
2. 报告必须带三元组坐标 `skill_version + model + data_profile`；
3. 设计态 ARS_d 只算 C，不得依赖链路运行结果；L 归运行态；
4. "不审结论对错，只审能不能被判对错"——必须在所有对外文档（PPT、报告、演示）上用一句话写死。

## 7\. 仪表：成本与预算

### 7.1 CU 定价

```
CU = tokens/1000 + latency\\\_ms/1000 + human\\\_min\\\*60
```

权重可配。1 人工分钟 = 60 CU ≈ 6 万 token，让"该问人还是该算"成为可比较的选择。

### 7.2 改造动作的价格表（示例，实际用拟合值）

|动作|影响维|典型 CU|说明|
|-|-|-|-|
|补 locator|L|0.5–1 / 条|解析输出定位到行/字段|
|原地改写规则（含 1 check + 3 fixture）|C、D|3.0 / 条|把"合理""适当"改成可判谓词；不新增规则条数|
|补字段|R|2.0 / 条|字段已在源里，只需映射|
|重跑验证|R、F|1–3 / 条|输入变更后重算|

### 7.3 预算与归因

`accept\\\_with\\\_grade` 必须记录：等级 + 原因码（BUDGET\_EXHAUSTED / LOW\_SEVERITY / DEFERRED / STRUCTURAL）+ 跳过的动作与价格 + 预算快照。

### 7.4 边际分析

对 5 档预算重复求"最省 CU 达到目标档"，得 `(CU, ARS)` 点列；差分即"再花 1 CU 能买多少分"；低于阈值（0.5 分/CU）标"边际枯竭"。
