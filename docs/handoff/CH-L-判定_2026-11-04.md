## 为什么不选“语义等价”

对 c-001 的副本仅在内存中改变 pe 的期望值，源 CSV 仍为 12，公司和 locator 保持原样：

| 反例 | A `resolve_bytes` | C `resolve_all` / line_lookup | C recompute |
|---|---|---|---|
| 期望值改成 13 | VALUE_MISMATCH | RESOLVED / verified | indeterminate / VALUE_MISMATCH |
| 删除期望值 pe | NOT_FOUND / EXPECTED_VALUE_MISSING | RESOLVED / verified | indeterminate / MISSING_FIELD |
| 期望值改成字符串 NaN | VALUE_MISMATCH / non_finite_number | RESOLVED / verified | indeterminate / NON_NUMERIC |

**边界反例差异 = 3/3**，不计入原始 100 条的差异率。
原包没有被改写；这些是函数级反例，未重新封装成已校验摘要的正式证据包。

原因：`evaluator.resolve_all` 调用 `_resolve_locator` 读取位置和检查公司，
没有校对 `expected_values`；数值检查在 C 的另一个步骤 `evaluate_claim` 中。
因此 C 能在复算步骤发现问题，但当前 L 可以仍记为成功。A 的 L/M15 口径要求读回值匹配。

## 给 C 的纯函数

```python
from assurance_ledger.core.claim import Locator
from assurance_ledger.ledger.resolver import resolve_bytes, ResolveResult

result: ResolveResult = resolve_bytes(
    Locator.model_validate(locator_json) if locator_json else None,
    expected_value,
    source_bytes=decoded_source_bytes,
    source_file="source.csv",
)
```

签名：`resolve_bytes(locator: Locator | None, expected_value=None, *, source_bytes: bytes | None, source_file: str) -> ResolveResult`。

调用不读取文件、网络、全量包或外部缓存。CSV 解析、文本归一化、非有限值拒绝及数值相对容差 `1e-6`
与原 `LocatorResolver` 共用实现；对零不添加绝对容差。原文件入口的白名单、路径和符号链接边界保留。
已有 34 个异常来源样本对新旧入口逐字段比对全部通过，并新增测试禁止纯函数读文件。

本函数只负责一个位置及数值匹配。C 先校验原始包和来源摘要，并继续保留：

1. 公司标识、claim 与输入绑定、主 locator 与字段映射检查
2. 必需的主位置及全部操作数，不因失败删除分母
3. 双跑一致性与 C 的原因码、计时和 L 输出结构

任何必要位置为 VALUE_MISMATCH、NOT_FOUND 或 NO_LOCATOR，都不能贡献 L 的成功分子。
不要把读取函数的三态直接改写成最终事实真伪；R 的规则求值仍由 C 负责。
