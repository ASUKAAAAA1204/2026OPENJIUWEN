# 全链路装配与效率设计

> 日期：2026-10-29｜配套：PRD v1.0、开源选型与自建边界
> 目标：在 32 天、3 人的约束下，让链路**功能不缺段、时延不失控、重复劳动为零**。

---

## 1. 端到端链路（7 段 + 1 条反馈）

```
[S0 规则侧 · 离线一次性]
  Skill 规则 ──解析──> 检查模板(check template) + severity 标注 + locator 规范
                              │  每 Skill 一份，缓存复用
                              ▼
[S1 采集 · 在线]  Rail ℋ_call / ℋ_task
  事件流 {claim_id?, kind, tokens, latency_ms, digest, ts}
        │
        ▼
[S2 claim 成型]  输出解析（一次 LLM）──> claim + locator
        │                                   └─失败──> structural debt
        ▼
[S3 目录实例化]  template × claim ──纯函数──> checks[]（含 cost 估计 / effect 先验 / severity）
        │
        ▼
[S4 调度]  policy + budget ──<5ms──> verify_now | defer | accept_with_grade
        │
        ▼
[S5 执行]  cheap-first + 缓存 + 超时 + 并行≤4
        │
        ▼
[S6 裁决]  执行结果 ──> grade(A/B/C/D) + assurance + debt 三类
        │
        ▼
[S7 交付]  账本(哈希链) ──> Studio 一屏 ──> 导出 ledger.json ──> verify
        ▲
        │
[S8 反馈 · 离线/批量]  人工复核 ──> 校准 p_fail 先验 ──> 演进 patch
```

**关键结构判断**：链路里有两处"一次性/离线"设计（S0 模板、S8 校准），它们把在线路径上的重复计算全部移走。**效率不是把每一步做快，是把不该在线上做的事挪到线下。**

---

## 2. 六个决定效率的搭配选择

### 2.1 一次采集，三处消费

Rail 事件同时喂三件事：成本模型、claim 归属、证据 digest。

**铁律**：任何模块都不允许为了拿数据而重复调用工具。重复调用会同时抬高成本（假账）和延迟（真慢）。

### 2.2 模板与实例分离

检查目录的"形状"由 Skill 规则决定，是**离线的**；每条 claim 只是把模板实例化（填 locator、算 cost），是**纯函数、O(1)**。

反例：每条 claim 都让 LLM 读一遍规则 → 200 条 claim 就是 200 次调用，成本爆炸且结果不可复现。

### 2.3 cheap-first + 达标早停

| 顺序 | 检查 | 典型成本 | 何时停 |
|---|---|---|---|
| 1 | line_lookup | ~0.05 CU | — |
| 2 | recompute | ~1 CU | — |
| 3 | cross_source | ~3 CU | 达到目标等级即停 |
| 4 | human_review | 60 CU | 除非等级要求或人工指定 |

目标等级可配（默认 A）。一条 claim 如果两项检查就够 A，第三项不执行——**这是省钱的唯一正确位置**（在调度后、执行前，而不是事后）。

### 2.4 缓存键同时解决"省"和"过期"

```
key = (claim_id, check_kind, input_digest, rule_version)
```

- 命中 → 复用结果，0 CU；
- 未命中但 `input_digest` 变了 → 判为 `stale` 债务，重跑。

**一个机制同时解决缓存与新鲜度**，不需要额外的时间窗口逻辑。这是本设计里最省事的一处。

### 2.5 同步决策、异步记账

| 动作 | 模式 | 预算 |
|---|---|---|
| 调度决策 | 同步 | p99 < 5ms |
| 检查执行 | 同步（并行≤4） | p99 < 2s |
| 成本落盘 / 链哈希 / 面板刷新 | 异步队列 | 不阻塞 |

记账永远不能挡在决策前面。演示时如果因为写盘卡住 300ms，评委会看见。

### 2.6 LLM 只出现两次

整条链路里 LLM 只在 **S2（claim 抽取）** 与 **S6.5（crux 的人话解释）** 出现，各一次，其余全是确定性代码。

理由很直接：LLM 是唯一的不可预测延迟源与不可复现源。**把 LLM 用在"生成检查"或"判断不确定性"上，是这类项目最贵的错误**——慢 10 倍、贵 5 倍、还不可复现。

## 3. 时延预算

| 段 | p50 | p99 | 备注 |
|---|---|---|---|
| S1 采集 | <1ms | 5ms | 进程内钩子 |
| S2 claim 成型 | 300ms | 900ms | 1 次 LLM，可批 |
| S3 目录实例化 | 1ms | 3ms | 纯函数 |
| S4 调度 | 2ms | 5ms | 200 claim 规模 |
| S5 执行 | 400ms | 2s | 并行 ≤4，含 1 次外部调用 |
| S7 面板首屏 | 800ms | 1.5s | 200 claim 只读视图 |
| 记账 | 异步 | — | 不参与预算 |

**端到端（一次完整运行，200 claim）**：目标 p50 ≤ 8s，p99 ≤ 20s。超过就说明有检查在串行排队或 LLM 被调了多次。

---

## 4. 六个交接点与不变量

搭配的本质是接口。六个交接点，每个只允许一个 owner：

| 交接 | 谁写给谁 | 不变量（违反即 bug） |
|---|---|---|
| C1 | Rail → 事件流 | 每条事件必有 `seq`、`ts`、`tokens`；`claim_id` 可空但不可错 |
| C2 | 事件流 → claim | claim 必有 `locator`，否则标记 `NO_LOCATOR`，不得静默丢弃 |
| C3 | claim → 目录 | 每个 check 必有 `cost`、`effect_prior`、`severity` 三件套 |
| C4 | 调度 → 执行 | 任何 `skip` 必带 `reason_code` |
| C5 | 执行 → 账本 | 每条 check 必有 `status` + `digest` + 实际耗时 |
| C6 | 账本 → 面板 | **只读**，面板不得触发重算 |

C6 值得单说：面板一旦能触发计算，刷新就会变成一轮新的运行，演示时最容易被点崩。

---

## 5. 降级链（每一层都有退路）

| 失败点 | 降级 | 影响 |
|---|---|---|
| Rail 无成本字段 | 离线日志估成本 | 精度下降，曲线仍可出 |
| claim 抽取失败 | 标 `NO_LOCATOR`，进 structural 债 | 少一条可验 claim |
| 成本模型未拟合 | 默认单价表 | 曲线可信度下降，可标注 |
| Studio 产物区不可扩展 | 报告节点 + 附件 | 体验下降，功能不丢 |
| 人工复核缺席 | 用先验替代，标注"未校准" | 诚实降级，不装 |

---

## 6. 三个不能省，三个可以省

**不能省**（省了就不是这个产品）：
1. `locator` 精度——没有定位就没有检查；
2. `digest` 与新鲜度——没有它就没有 `stale` 债务；
3. `reason_code`——没有它，"没验"就重新变成不可见。

**可以省**（32 天内）：
1. 跨 Skill 聚合视图（一张表的事，不急）；
2. 学习型策略（解释不了，反而扣分）；
3. 签名与透明日志（没有验证方，做了是表演）。

---

## 7. 并行切分：三人不打架

接口先冻结（C1–C6），然后按写作用域切：

| 人 | 负责 | 写作用域 | 周 |
|---|---|---|---|
| A | Rail 埋点、事件流、缓存、成本拟合 | `rail/`、`cost/` | W0–W2 |
| B | 模板、定价、调度、等级、债务 | `engine/` | W1–W3 |
| C | 账本、校验器、Studio 面板、导出 | `ledger/`、`ui/` | W2–W4 |

**只靠接口对齐、不共享文件**，是唯一能让三人在 32 天里并行的办法。任何"先写再合并"的设计都会在 W3 崩塌。

---

## 8. 效率指标（验收时一起看）

| 指标 | 目标 | 含义 |
|---|---|---|
| 每 claim 平均成本 | ≤6 CU | `always` 基线约 12 CU |
| 缓存命中率 | ≥60%（二次运行） | 同一 Skill 重跑 |
| 重复工具调用率 | 0 | 同 digest 不重复调 |
| 单 claim LLM 调用 | ≤2 次 | 超过说明设计漏了 |
| 面板首屏 | p95 ≤1.5s | 200 claim |
| 端到端运行 | p95 ≤20s | 200 claim |

---

## 9. 反模式（会让链路变慢、变贵、变不可演示）

1. **用 LLM 做不确定性分类**——慢 10 倍、贵 5 倍、不可复现。四象限应完全由规则与 digest 推导。
2. **每条 claim 重新解析规则**——O(n×rules)，200 条就是灾难。
3. **同步等人工**——演示必挂；人工只能进排队。
4. **把策略引擎放进热路径**——OPA/Rego 适合准入，不适合每 claim 一次。
5. **双写两套日志**——两份真相，审计场景直接失效。
6. **先做 UI 再定契约**——契约一变，UI 全返工。
7. **在面板里触发计算**——刷新即运行，必然点崩。

---

## 10. 一句话总结

**全链路的最优搭配不是"每层都用最好的组件"，而是：**
**离线能算的全部离线（模板、校准），一次能拿的绝不再调（采集、缓存），必须快的绝不等慢的（决策 vs 记账），不确定的全部降级（LLM、平台、人工）。**

功能最优化来自"每段都有人负责且不重叠"；效率最大化来自"线上只跑必须在线跑的东西"。

## 11. 依赖清单（按阶段标注）

标记：**必需** = 没有它链路不成立；**可选** = 有更好、没有也能演；**不引入** = 明确拒绝并给理由。

### 11.1 总表

| S3 目录实例化 | —（标准库） | — | 纯函数 | — | — |
| S4 调度 | —（标准库 heapq） | — | 贪心调度 | — | — |
| S5 执行 | semgrep | LGPL-2.1 | 代码类检查（副场景） | 可选 | **CLI 子进程** |
| S5 | httpx | BSD-3 | 外部调用（若 demo 需联网） | 可选 | 库 |

### 11.2 明确不引入（附理由）

| 项目 | 许可证 | 它解决什么 | 为什么不用 |
|---|---|---|---|
| Langfuse | MIT | LLM 可观测平台 | 双份真相；span 模型没有 claim 概念 |
| Arize Phoenix | Elastic License 2.0 | 轨迹可视化 | **非 OSI 许可**（ELv2），与 Apache-2.0 主仓叠放有解释成本；且同为双真相 |
| OPA / Rego | Apache-2.0 | 准入策略 | 我们的核心是数值优化，塞进 Rego 会不可调试；进热路径更慢 |
| Cedar | Apache-2.0 | 同上 | 同上 |
| Sigstore / cosign | Apache-2.0 | 签名与透明日志 | 无验证方社区，签名是表演；只留 `signer_kid` 字段 |
| SPIFFE/SPIRE | Apache-2.0 | 工作负载身份 | 需要运维一套身份基础设施，32 天不划算 |
| Keycloak | Apache-2.0 | 人员身份 | 同上；Studio 自带会话足够 |
| Presidio | MIT | PII 识别 | 合成数据场景不需要；真实数据场景再引入（1 人日） |
| Great Expectations | Apache-2.0 | 数据质量断言 | 与"回源重算"重叠，多一套规则语言 |
| DuckDB | MIT | 本地分析库 | 200 条 claim 用 dict/list 足够 |
| OR-Tools | Apache-2.0 | 精确背包/调度 | 贪心在 200 条规模上差距 <2%，引入重求解器无收益 |
| reportlab | BSD | PDF 导出 | 浏览器打印足够，省一个依赖 |

### 11.3 许可证纪律

| 规则 | 说明 |
|---|---|
| 只用 MIT / Apache-2.0 / BSD | 与主仓 Apache-2.0 兼容，无附加义务 |
| **避开 AGPL** | 网络服务条款会传染到整个作品 |
| **LGPL 只作独立进程调用** | semgrep 走 CLI 子进程，不链接其库；声明里写清"外部命令调用" |
| **不 vendor** | 依赖装进环境、不复制源码进仓库——这样"第三方代码占有效代码量"不会因依赖膨胀 |
| 不引入 ELv2 类许可 | 非 OSI 许可在开源作品里解释成本高 |

### 11.5 仓库结构（依赖与 SBOM 的位置）

```
repo/
├── LICENSE                  # Apache-2.0
├── README.md
├── THIRD_PARTY_NOTICES.md   # §11.4 的表
├── sbom.cdx.json            # CycloneDX 生成
├── pyproject.toml           # 依赖锁
├── rail/  engine/  ledger/  ui/
└── docs/  (PRD、技术报告、复现脚本)
```

`THIRD_PARTY_NOTICES.md` 与 `sbom.cdx.json` 必须在 W1 之前生成一次，之后每次加依赖都更新——**最后一周补这个，一定漏。**
