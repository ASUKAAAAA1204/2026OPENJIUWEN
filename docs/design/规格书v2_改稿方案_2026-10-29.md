## 0. 先把"够"定义清楚，否则改不完

三个词在旧稿里都是形容词，改稿的第一步是把它们变成可判定的句子。

| 目标 | 旧稿的默认理解 | v2 的定义 | 为什么必须换 |
|---|---|---|---|
| 创新 | "世界上第一个" | **在别人已有的位置上，多交付一个别人没有的对象或判定** | "第一"已被 LEDGER / VeriHarness 占掉，且不可证 |
| 可行 | "32 天能写完" | **关键路径上只有一个未知，且这个未知在 W0 一天内能证伪** | 旧稿有 4 个未知（钩子、Skill 格式、demo 载体、Studio 集成），任一失败都要重做 |
| 壁垒 | "别人复制不了" | **复制的成本结构：踩坑数 × 数据增长 × 迁移成本** | 32 天内不存在"复制不了"；但存在"复制要重踩 3 个坑、且数据在对方手里" |

### 三者不互相拆台的唯一原则

> **创新落在"产物"和"数据"上，不要落在"算法"上。**

- 算法创新最贵（研究周期）、最难证（要 benchmark）、最容易被前人占位；
- 产物创新最便宜（1–2 天就能做出一个别人没有的对象）、最好演示（现场可验）；
- 数据创新会自己长大（每次人工复核都变厚），这正是壁垒唯一真实的来源。

旧稿把创新放在"四象限分类器"和"分歧消解协议"上——都是算法位；v2 把创新挪到"证据包"和"不可裁决声明"上——都是产物位。**同一个工作量，评价口径完全不同。**

## 1. 创新：四层，每层都要有一个"别人没有的东西"

四层不是四个功能，是四个不同性质的"新"。评审只要有一层立住，创新分就不会低；四层都立住，才叫"足量"。

### L1 产物：证据包（Evidence Bundle）

**别人有什么**：LEDGER 有给人看的 trace graph（审阅界面）；VeriHarness 有对 artifact 的选择与修订（方法）。
**别人没有**：**随结论一起交付、可离线自校验的一份包**。

包里有：结论 + 证据指针（精确到文件/行/字段/工具返回）+ 四象限不确定性 + 置信度与逐项扣分 + 裁决结果或 crux + 哈希链。
演示方式：`verify bundle.json` → 通过；改一个字节 → 断链。**这个演示不需要任何文献背书，也无法被反驳。**

### L2 判定：把"不可裁决"做成一等输出

**别人有什么**：分歧消解（要么收敛，要么选一个）。
**别人没有**：**claim 级的 `crux` 状态**——裁决器明确输出"我判不了，缺的是这个东西"。

这是产品上最诚实、也最容易被记住的一屏。它把"让 Agent 说不知道"从一句口号变成一个结构化对象：

```yaml
adjudication:
  state: crux
  crux:
    point: "两个数据源日期相同、权威性均有争议"
    paths: [ {agent: analyzer, source: api, distance: direct},
             {agent: auditor,  source: export, distance: direct} ]
    needs: "该字段的官方口径（交易所披露）或第三方交叉核验"
```

**为什么算创新而不是偷懒**：主流做法是在无法判断时退化成一个隐式启发式（旧稿就是"时间→权威→格式"排序），用户看不出这一票是怎么投的。显式 `crux` 把不确定性变成了可分配的任务。

### L3 度量：不确定性画像（Uncertainty Profile）

**别人有什么**：单次任务的验证分数。
**别人没有**：**跨 Skill、跨任务的四象限分布**——"这个生态里 Agent 的不确定性，主要来自输入缺失，而不是模型不确定"。

成本极低（一次统计 + 一张图），但它同时干三件事：给答辩一个可复算的数字、给技术报告一个像研究的章节、给壁垒一个会随时间变厚的资产（§2）。

### L4 载体：Rail 级注入 + 演进回流

**别人有什么**：per-agent 的包装、per-skill 的插件。
**别人没有**：**在框架扩展点上写一次，所有走该 Framework 的 Agent 都获得证据能力**，并且证据包能作为自演进的反馈源。

这一层是"只有在这个生态里才能做"的一层，也是 FAQ Q17「生态利用深度」加分的真正落点。它的成立依赖两个已确认的平台事实：Rail 的钩子空间 ℋ = ℋ_invoke ∪ ℋ_call ∪ ℋ_task，以及已上线的双层自演进（产出 `evolutions.json` 的 patch）。

### 必须同时写进去的「不主张」清单

放在技术报告"与既有工作的关系"一节，主动写，不等评委问：

- 不主张首个语义证据链（LEDGER, arXiv:2608.18398, 2026-08-19）；
- 不主张首个 agentic verification（VeriHarness, arXiv:2610.00972, 2026-10-01）；
- 不主张"对齐"任何标准草案（AAT 是 individual draft，明写 no formal standing）。

主动引用这三条，把比较的战场从"谁先提出"挪到"谁交付了可用产物"——**这是唯一对你有利的战场。**

## 2. 壁垒：从"防复制"改成"复制的成本结构"

旧稿的壁垒论证是"组合起来就是世界上第一个"——这是防复制叙事，32 天内不成立，且比赛不打这个分。v2 换成三段可辩护的成本结构：

### 2.1 集成深度（复制者要重踩的坑）

| 坑 | 为什么别人会踩 | 我们的位置 |
|---|---|---|
| Rail 的优先级 p_ρ 与可见性门控 g(ρ,u) | 不知道优先级会被别的 Rail 覆盖；不知道门控决定能读到多少参数 | W0 实测，写进技术报告 |
| Studio 集成路径 | 官方要求 Demo 预部署进 Studio，但文档稀薄 | W4 打通，形成私有 know-how |
| 演进引擎会改写 Skill 文本 | 把验证逻辑写进 prompt 的人，三个月后逻辑会被 patch 掉 | 逻辑放 Rail 代码，Skill 只留配置 |

**这三条都不写在公开文档的显眼处**，是真实的时间成本。这就是"集成深度"的含义：不是技术多难，是别人要重新走一遍。

### 2.2 数据资产（唯一会自己长大的东西）

每一次在 Studio 里被人工推翻的标记，都可以沉淀成一条 `failure pattern`：

```
{skill: X, quadrant: assumption, pattern: "行业均值口径", corrected_by: human, at: ...}
```

32 天攒不到"数据壁垒"，但能攒到 20–50 条真实模式 + 一个可扩展的台账结构。**答辩时不要说"我们有数据壁垒"，要说"这是壁垒的种子，它每被用一次就厚一点"。** 后者可信，前者会被追问"多少条"。

### 2.3 接口位置（降低替换意愿）

证据包格式一旦被第三方 verifier 接受，替换成本就从"改一个库"变成"改一套校验和归档流程"。这是标准化的经典机制，也是把 §3.1 里"参考 AAT 字段语义"唯一值得保留的理由：**不是为了说"我们合规"，是为了让包能被别人验。**

### 壁垒自检

| # | 判据 | 本方案 |
|---|---|---|
| 1 | 复制者要重踩 ≥3 个坑 | 是（上表） |
| 2 | 有一个随使用增长的资产 | failure pattern 台账 |
| 3 | 有一个提高迁移成本的接口 | 可离线校验的证据包 |
| 4 | 18 个月后仍成立（不绑死某个 API 名） | 是（架构按"钩子/产物/校验"抽象，Rail 只是当下实现） |

### 3.1 单一主线（任何超出这条线的都进"未来工作"）

### 3.3 三道闸门（不达标就砍范围，不砍演示）

## 5. 六段成稿（可直接替换旧稿）

### 5.1 定位（替换原〇开头）

> **给 Studio 里每个 Agent 的结论配一张能签字的凭证。**
> 依据在哪、缺什么、和别人不一致时听谁的——一屏看完，可离线校验。
>
> 用户不是"Skill 开发者"，是**要对结论负责的人**：投研合规审核员、代码评审负责人、交付前的技术负责人。
> 他们现在的困境不是"Agent 做得不对"，是"Agent 做得对不对，我说不清"。

### 5.2 创新点（替换原五全部）

（用 §1 的四层 + 不主张清单，逐层写"别人有什么 / 别人没有 / 我们怎么做 / 现场怎么证"四行。）

### 5.3 架构（替换原二模块 1）

```python
class EvidenceRail(Rail):          # 挂在 Agent Framework 的生命周期钩子上
    priority = 10                  # p_ρ：先于业务 Rail 执行

    def on_call(self, ctx):        # ℋ_call：模型/工具调用
        rec = {
            "record_id": new_id(),
            "agent": ctx.agent_id,
            "tool": ctx.tool_name,
            "params_digest": digest(ctx.params),
            "phase": "pre_execution",     # 记录先于动作
            "prev_hash": self.chain.head,
        }
        self.recorder.write(rec)                       # 先写
        result = ctx.proceed()
        self.recorder.write({**rec, "phase": "post_execution",
                             "result_digest": digest(result)})

    def on_task(self, ctx):        # ℋ_task：任务迭代
        if ctx.is_final:
            self.bundler.close(ctx.task_id)            # 生成证据包
```

要点三条（写进报告，是"深度"的证据）：
1. `phase: pre_execution`——记录写在动作之前，消掉"日志是不是事后补的"这个最本能的怀疑；
2. `prev_hash` 串联——改、删、换序、截断四类篡改全部可检；
3. **可见性门控 g(ρ,u) 决定能读到什么**——这是 W0 必须实测的未知，也是技术报告里"我们踩过的坑"。

### 5.4 证据包 schema（替换原二模块 2 的 yaml）

```yaml
bundle:
  id: evb-20261209-0007
  claim:
    id: c-001
    statement: "A 的 PE 低于行业均值"
    locator: {file: "industry.csv", row: 15, field: "PE"}
  evidence:
    - {kind: tool_call, ref: "finance_api.get_pe", locator: "result:12.3",
       digest: "sha256:...", captured_at: "...", distance: direct}
    - {kind: rule, ref: "pe_compare.v2", locator: "L3", distance: direct}
  uncertainty:
    missing:    [{field: "创业板PE", why: "未取数", severity: high}]
    conflict:   [{topic: "PE", values: [12.3, 11.8], sources: [api, export]}]
    assumption: [{text: "均值用算术平均", rule_id: "pe_compare.v2", verified: false}]
    uncovered:  [{action: "市值加权比较", scenario: "不同市值可比性"}]
  adjudication:
    state: crux                 # resolved | crux | insufficient
    crux: {point: "...", paths: [...], needs: "..."}
  confidence:
    value: 0.72
    basis: {completeness: 0.85, consistency: 0.60, coverage: 0.70}
    deductions: [{reason: missing_high, delta: -0.15}]
    note: "非概率；仅用于排序与告警"
  integrity:
    prev_hash: "sha256:..."
    record_hash: "sha256:..."
```

相对旧稿的改动：删 `role` 字段（冗余）、加 `locator` 统一规范、加 `distance`、加 `adjudication.crux`、加 `phase`、把 `derived_confidence` 的 magic number 换成 `deductions` 列表（可解释、可复算）。

### 5.5 Skill 包与 Studio 交付（替换原二模块 5）

```
verification-rail/
├── SKILL.md            # frontmatter: kind: swarm-skill, teammate_mode, roles[]
├── roles/
│   └── auditor.md      # 审计员角色：读 bundle，提 crux
├── workflow.md         # Mermaid: collect → classify → adjudicate → bundle → export
├── bind.md             # record_policy（分级采样）、quality gates、降级策略
└── dependencies.yaml   # 依赖清单（≤30% 第三方）
# evolutions.json 由运行期演进引擎写入，不手工维护
```

**Studio 交付三步**（这是"完成度/用户体验"的唯一得分点）：
1. Rail 作为依赖随应用部署，应用启动时注册（不改 Studio 源码）；
2. Studio 里选中该应用 → 跑一次 → 产物面板出现"证据包"节点；
3. 点开 = 一屏（结论 / 证据 / 缺口 / 裁决或 crux / 校验状态），按钮 = 导出 + 篡改演示。
   兜底：产物面板不可扩展时，用报告节点输出结构化 Markdown + 附件。

## 8. 答辩三问（背下来）

**Q1：这和 LangSmith / OTel / HoneyHive 有什么区别？**
> 他们记录 Agent 调了什么，我们交付一个能签字的凭证：结论、依据、缺口、以及"我判不了"的那部分。现场可以验——改证据包一个字节，校验立刻失败。

**Q2：LEDGER 已经做了 claim-to-evidence，你新在哪？**
> LEDGER 做的是给审阅者看的图，回答"这个结论怎么来的"；我们做的是随结论一起交付的包，回答"这个结论现在能不能签字"。他们不标不确定性、不裁决、不出 crux——这三件事是我们的。

**Q3：壁垒在哪？**
> 三段：集成深度（Rail 的优先级与门控、Studio 集成、演进会改写 Skill 文本这三个坑，别人要重踩）；数据资产（每个被人工推翻的标记变成一条 pattern，越用越厚）；接口位置（可离线校验的包，一换就得改归档流程）。32 天内这三样都只是种子，但种子是可验证的。

**不要说**：世界第一 / 256 个 Skill / 对齐 IETF 标准 / 通用。
