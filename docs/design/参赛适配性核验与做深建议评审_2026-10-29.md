## 0. 三句话结论

1. **方向对，规格书不能直接当施工图用。** 方案押注的"在 Swarm 流程里插一层拦截"这件事，平台**真的支持**——扩展点叫 **Rail**（生命周期钩子 ℋ = ℋ_invoke ∪ ℋ_call ∪ ℋ_task，带 handler 与优先级），比方案设想的还完整。但规格书对平台的五处具体描述全部失实：扩展点名字、"256 个 Skills"、Skill 包结构（没有 `rules/`、没有 `scripts/`）、`human_session` 算子、以及两个被拿来当 demo 的被测 Skill 根本查不到。社区专家评委一眼就能看出这份材料没读过平台文档。

2. **真正的适配风险不在技术，在交付形态。** 官方提交格式说明要求 Demo **预部署并集成进 OpenJiuwen Studio、基于 Studio 界面演示**；创意阶段评的是"创新性/实用性/技术可行性/场景价值"，DEMO 阶段评的是"完成度/用户体验/技术难度/商业价值"。规格书通篇是 SDK 视角，没有一页是"用户在 Studio 里看到什么"，六个维度里有一半没有落点。

3. **那段"做深"建议：事实基本可靠（10 条里 9 条成立），判断有一半可用，但作为决策文档不及格。** 可用的：环境检验式裁决、crux、哈希链、边界声明、以及"语义证据链不能再当创新点"这个判断。不可用的：证据距离公式、Merkle/签名、以"对齐草案"为壁垒的叙事。**不及格的地方在于：16 条建议 0 条人日、把推论写成事实、把最强的一句埋在最后、以及完全没对账比赛只剩多少天。**

> **时间警告：** FAQ 写创意提交截止 **2026-11-10**，但官方 9-17 发布的启动公告写的是 **10 月 30 日**，两份官方材料冲突（详见 §1.1）。如果以早的那个为准，截止就是明天。**今天必须发邮件向 contest@openjiuwen.com 确认**，并按"最早的那个"排期。

## 2. 方案核验

### 2.1 五处平台失实（这一节最要紧）

规格书对 openJiuwen 的所有具体描述，方向都对，细节全错。逐条对：

| # | 规格书写的 | 平台实际 | 后果 |
|---|---|---|---|
| 1 | "Interceptor 层"，插入三个位置 | 扩展点叫 **Rail**：挂在生命周期钩子上，钩子空间 **ℋ = ℋ_invoke ∪ ℋ_call ∪ ℋ_task**（调用级、模型/工具调用级、任务迭代级），ρ = (ℋ_ρ, f_ρ, p_ρ)，f 是 handler、p 是优先级，另有模型/工具异常钩子与可见性门控 g(ρ,u) | 名字错不要紧，"不知道有优先级和可见性门控"才要紧：优先级决定你的证据收集会不会被别的 Rail 覆盖，门控决定你能不能看到参数 |
| 2 | "openJiuwen 256 个 Swarm Skills" | 官网口径 **250**；且 Hub 已升级为 Agentic Hub，混装 Swarm Skill、单 Skill、插件、连接器、专家团——256 很可能是"全部资产类型"的计数 | 数字被当场纠正，连带削弱"空白地带"的论证 |
| 3 | Skill 包 = `SKILL.md` + `roles/` + `rules/` + `scripts/` | 实际是 **5 件套**：`SKILL.md`（frontmatter 含 `kind: swarm-skill`、`teammate_mode`、`roles[]`）+ `roles/` + `workflow.md`（Mermaid 拓扑）+ `bind.md`（budgets、quality gates、降级/重试）+ `dependencies.yaml`，运行期还有 `evolutions.json`。**没有 `rules/`，也没有 `scripts/`** | 模块 5 那张目录树直接不成立；"可复用 Skill 库"没有落地位置 |
| 4 | "SwarmFlow 已升级出 budget、human/human_session、agent_session 等算子" | 真实算子是 `budget() / parallel() / compact() / pipeline() / agent_session() / human() / return`；**没有 `human_session`**，团队级人工介入用 HOTS/HITS 表达 | 写进方案会在答辩时被要求现场演示一个不存在的 API |
| 5 | demo 套在"A股持仓智囊团"和"代码评审专业组"上 | 这两个名字在官网、Hub、仓库、博客里**零命中**（生态里确有"短视频制作团队""旅行规划"这类中文命名，风格像但这两个查无实据） | 最严重：T5"套在两个已有 Skill 上"的被测对象不存在，通用性论证整体悬空 |

另有第 6 处，是"没写"而不是"写错"：**没有 Studio 集成方案**（§1.2）。

**这六条合起来说明一件事：这份规格书是在没读平台文档的情况下写出来的。** 它对"要做成什么样"的判断可能是对的，但对"在这个平台上怎么做"的每一个具体断言都不可靠。修复方式不是逐条改文字，而是重写模块 1 与模块 5，并把 demo 换成真实存在的载体。

### 2.2 好消息：Rail 让方案里最难的部分变成可做

规格书最大的技术赌注是"能不能在 Swarm 里插进去"。答案是能，而且比设想的更合适：

- **ℋ_call 覆盖模型与工具调用**——证据收集的天然落点，比"包一层 tool proxy"更干净；
- **ℋ_task 覆盖任务迭代**——可以做"每个任务节点的证据快照"，而不是只在最终输出上补一条哈希；
- **优先级 p_ρ**——保证证据 Rail 在其他 Rail 之前/之后执行，顺序可控；
- **可见性门控 g(ρ,u)**——决定了你能读到多少参数，也就决定了证据链的粒度。**这一条必须在 W0 的一天里实测**，否则 T1 的"≥90% 捕获率"仍然是空话。

也就是说：**方案里最贵的那个假设反而成立了，而最便宜的那些描述全错了。** 这个组合很好处理——不用改方向，改施工图。

### 2.3 真正的适配风险：SDK 视角 vs Studio 视角

"工具还是作品"这个说法要修正。官方提交格式说明明确把参赛物定义为 **Agent Tool**，并允许它以工具形态存在——所以"这是个开发者工具"本身不是问题。问题是它要求这个工具 **预部署、集成进 Studio、用 Studio 界面演示**，而规格书的产出物是"一个 JSON 报告 + 一个独立面板"。

评委在 DEMO 阶段看的是：打开 Studio、加载被测 Skill、跑一次、**在 Studio 里**看到证据包展开、看到篡改后校验失败。这条路径在规格书里不存在。而它恰好是"用户体验"和"完成度"两项的唯一得分点。

结论：**把"证据包"从一个离线 JSON 变成 Studio 里的一个可视产物**，这不是包装，是交付形态的必要条件。

### 2.4 平台能力事实表（可直接写进技术方案）

| 能力 | 事实 | 对本方案 |
|---|---|---|
| 五层架构 | DeepAgents（JiuwenSwarm / JiuwenSymbiosis / DeepSearch）、Agent Studio、Agent Framework（agent-core / agent-gateway / agent-memory）、Agent Distributed Runtime、Agent System Service（AgentOS）；WorkSwarm 是基于 JiuwenSwarm 的办公/编码工作台 | 证据层应落在 Agent Framework（agent-core 的 Rail），不是 Studio 的低代码层 |

### 2.6 最贵的错误："世界上第一个"

规格书里有三处"世界上第一个"，结尾还有"三者第一次在一个可复用 Skill 里完整落地"。这些话在答辩现场是负资产：

- LEDGER（arXiv:2608.18398，2026-08-19）已经在做 claim-to-evidence trace graph，摘要原句是 "visibility alone still leaves reviewers to reconstruct which actions, artifacts, and validation steps matter for a particular conclusion"——和规格书第 24 行的立论几乎同义。
- 更要命的是，它把你拖进一个你赢不了的战场。读者看到"世界第一个语义证据链"，就会去比"证据链"，而那是 LEDGER 的主场；没人会去比"证据包能不能在 Studio 里被第三方离线校验"，而那才是你能赢的地方。

替换原则：**只声明能当场演示的东西，不声明"第一"。** 例如"每个结论可导出为一份带哈希链、可离线校验的证据包——现场改一个字节即断链"。这句话不需要任何文献背书，也无法被反驳。

### 3.1 事实核查

逐条回原文核对。判定：✅ 成立 / ⚠️ 部分成立或需改表述 / ❌ 不成立。

| # | 原文说法 | 核查 | 影响 |

**AAT 三处必须改：**

1. **它不是标准，是个人草案。** IETF 页面明写 "not endorsed by the IETF"、"no formal standing"，状态是 "Active Internet-Draft (individual)"。说"对齐标准"会被一句"哪个 WG"问穿。
2. **不是"五个必填字段"。** §3.1 约 13 个必填（record_id、timestamp、agent_id、principal、session_id、action_type、action_detail、outcome、trust_level、parent_record_id、prev_hash 等）；摘要那五个只是点名举例。规格书按"至少三个"设计，是把举例当全集。
3. **标准映射是参考性的。** §11 自己声明 informative、"不是合规评估"。所以"覆盖 Annex III 记录义务"不能说。

**顺手捡两个比哈希链更值钱的点（原文漏了）：**

- **`record_phase: pre_execution`**（草案 §4）：高风险动作的记录要写在动作**之前**，否则无法证明"策略在动作前就生效"。对本方案近乎零成本（一个字段 + 先写后调），但能一句话消掉评委会最本能的怀疑——"日志是不是事后补的"。
- **Recording Independence**（§5.2）：草案明说自记录证据强度弱，独立记录器要在被审计进程之外。这正好把"Rail 在框架层、Agent 进程内"这个软肋点出来，也给出解法：**证据包由 Rail 采、由外部 verifier 校验**。这一条比"我们做了哈希链"值钱得多，且不需要实现签名。

### 3.2 逐条判定

判定口径只有三条：**32 天能不能做出来**、**做出来评委看不看得见**、**看不见的能不能在答辩里兑成一句话**。

| # | 建议 | 判定 | 成本 | 对评分的作用 | 具体做法 |
|---|---|---|---|---|---|
| 1 | resolver 从"预设排序"改为"环境可执行检验" | **采纳（核心）** | 3–4 人日 | 技术难度 ↑↑，支撑"机制创新" | 只做 2 个 checker：数值回源重算、代码行号复核 |
| 2 | crux 隔离：裁决不了就结构化呈现 | **采纳** | 1 人日 | 差异最强的一屏，评委会记住 | 输出 `{crux, 双方证据路径, 缺口, 需补什么}`，Studio 里单独一栏 |
| 3 | 哈希链 + content fingerprint | **采纳** | 1 人日 | "改一个字节即断链"是现场最硬的演示 | SHA-256 前序链 + 指纹 + `verify` 命令 |
| 4 | 对齐 IETF AAT 最小子集 | **降级** | 0 | 加分有限、风险不低 | 报告里写"记录结构参考 AAT 草案"，**不说"兼容/对齐"** |
| 5 | Merkle / ECDSA / 外部时间锚 | **不采纳** | — | 32 天内无演示价值 | 进"未来工作" |
| 6 | 区分 record / decision reproducibility | **采纳为边界声明** | 0 | 答辩防守好句 | 技术报告一页 |
| 7 | 四象限重构为可组合原语 | **条件采纳** | 0.5 人日 | 内部质量，评委看不见 | 拆 4 个独立函数 + 统一返回；**不做**注册表/版本化 |

| 10 | 用控制面事件做时间锚 | **条件采纳（已确认真实算子）** | 0.5–1 人日 | 生态深度加分的硬证据 | 记 3 类：`human()` 介入、`budget()` 截断、`agent_session()` 跨阶段；**别写 `human_session`** |
| 11 | 以合规时间线做路线图 | **降级为答辩 1 页** | 0 | 与赛事地域弱相关 | 一句话带过 |

| 15 | "中等偏上工程壁垒"作结论 | **不采纳为叙事** | — | 比赛不打壁垒分 | 换成"可演示差异 + 生态深度" |
| 16 | 叙事重心从"证据链"转向"验证层" | **采纳，但要换理由并补答案** | 0 | 决定整份材料骨架 | 见 §4.2 |

**第 12 条为什么能救活（原建议的逻辑漏洞 + 修法）：**

原建议说"失败反馈回流成验证 Skill 的新条目，形成数据壁垒"，但没回答：**demo 里没有真实用户，失败反馈从哪来？** 两个来源都不成立——LLM 自评正是它自己批判的东西，人工标注 32 天攒不出数据。

但平台的演进机制给出了第三条路，而且是现成的：openJiuwen 的自演进引擎吃的就是**执行轨迹 + 用户反馈**，产出是 `evolutions.json` 里的 patch，可回滚、可合并。所以本方案的角色应该反过来——**不去造一个自演进循环，而是成为它的反馈供给方**：

```
证据包里的"被人工推翻的不确定性标记" → 结构化 failure record → 演进引擎的 PATCH 输入 → Skill 下一版
```

这样：(a) 反馈来源真实（人在 Studio 里点一下"这条标错了"）；(b) 不需要自己造引擎；(c) 天然是"生态深度"加分。

**但有一个必须写进架构的约束：** 演进引擎会改写 `SKILL.md` / `roles/` / `workflow.md`。所以**验证逻辑绝不能写成会被改写的 prompt 或 rules 文本**，必须落在 Rail 的代码里，Skill 侧只留配置。这一条原建议完全没意识到，而它决定了方案三个月后还在不在。

### 3.3 这份建议本身的五个问题

1. **引用纪律。** 把摘要里没有的百分比（0.8 分）、把推论（rollout 共享误读）、把举例（五个必填字段）当事实用。技术报告里每个外部数字都该带 arXiv 编号与章节。
2. **威胁评估的方向反了。** LEDGER 是 cs.HC 的 trace & review 系统，抢的是"记录"这个词，不是你交付的东西。"叙事重心必须转移"成立，但理由要换成：**记录本身回答不了场景价值/用户体验/商业价值，而这三项占评分一半。**
3. **没有一条带人日。** 16 条建议 0 条成本。采纳项加起来约 **8–10 人日**——在只剩 24–26 个可写代码的日子里，等于砍掉 Studio 集成或整个副 demo。
4. **层级混乱。** 工程增量（哈希链）、研究增量（crux）、叙事增量（合规路线）、生态增量（自演进）混在一张清单，没区分"32 天内做"和"答辩时说"。
5. **最强的一句被埋在最后。** "LEDGER 的存在改变了叙事重心"是全文唯一会改变决策的句子，却放在第七节末尾。决策文档应当倒过来写。

（另有一处硬伤：建议里反复用"openJiuwen Swarm 的 256 个 Skills""human_session""A股持仓智囊团"作为论证支点，而这些都与平台事实不符——它和规格书是同一个信息源，同一个错误。）

### 3.4 值得原样保留的三点

- **"verifier 从不通过阅读 rollout 来打分，每个 verdict 都绑定到一次可执行 check"**——这条纪律是把 demo 从"演示"变成"验证"的关键，应写进技术报告的方法一节。
- **"把边界本身作为设计输入"**——主动声明不适用于长文叙事型 Skill，比声称通用更抗追问。
- **"证据膨胀是一等约束"**——32 天的 demo 里不存在，但它让评委相信你想过生产，一页就够。

## 4. 修正后的方案

### 4.1 一句话定位

> **给 Studio 里每个 Agent 的结论配一张"能签字的凭证"**——依据在哪、缺什么、和别人不一致时听谁的，一屏看完，可离线校验。

用户不是"Skill 开发者"，是**要对结论负责的人**：投研合规审核员、代码评审负责人、交付前的技术负责人。这一换，六个维度里的场景价值/商业价值/用户体验才有落点。

### 4.2 创新点重写（替换三句"世界第一"）

| # | 声明 | 为什么站得住 | 现场怎么证 |
|---|---|---|---|
| 1 | **产物**：每个结论一份可携带、可离线校验的**证据包**（定位 + 四象限 + 置信度扣分项 + 裁决/crux + 哈希链） | LEDGER 产出给人看的 trace graph，VeriHarness 产出对 artifact 的选择；都不产出"随结论交付、可被第三方复核"的包 | 现场 `verify`：改一字节即失败 |
| 2 | **机制**：裁决先回源到**可执行检验**；检验不了就输出 **crux**，不硬选数据源 | 规格书原方案是"时间→权威→格式"的排序，那是排序不是裁决；"承认不可裁决"是两篇论文都没有的产品行为 | 3 个 case：可裁决 / 不可裁决 / 证据缺失 |
| 3 | **载体**：做成 **Rail 级**的验证层，写一次对整个 Framework 生效，而不是逐个 Skill 包装 | Rail 是框架自己的扩展机制（ℋ_call/ℋ_task），这是 FAQ Q17"生态利用深度"的最强证据 | 一个 Rail 同时给两个不同 Agent 出证据包，业务方零改动 |
| 4 | **度量**：四象限不确定性在真实 Skill 上的**分布画像** | 最便宜、最像研究、也最像产品的一页 | 一张分布图 + 50 条样本附录 |

**明确不主张**（写进技术报告"与既有工作的关系"，主动引用而非回避）：不主张首个语义证据链（LEDGER, 2608.18398）；不主张首个 agentic verification（VeriHarness, 2610.00972）；不主张"对齐"任何标准草案。
