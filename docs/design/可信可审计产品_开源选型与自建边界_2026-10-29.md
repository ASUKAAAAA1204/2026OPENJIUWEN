# 完整「Agent 可信 / 可审计」产品：开源选型、缺口与自建边界

> 日期：2026-10-29
> 用途：直接喂给技术报告的"第三方依赖声明"与"与既有工作的关系"两节
> 结论先说：**可信/可审计的基础设施已经有八成的成熟开源件；真正缺的只有一层——"验证的决策层"。我们自主要做的，恰好就是那一层。它的重要性不在代码量，在于它不可被任何一个库替换。**

---

## 1. 一个完整产品要覆盖哪些层

把"可信 / 可审计"拆成八层，每层回答一个不同的问题：

| 层 | 回答的问题 | 成熟开源/标准 | 决策 |
|---|---|---|---|
| L1 采集 | Agent 做了什么 | OpenTelemetry、OpenInference、Langfuse、Phoenix | **用 openJiuwen Rail，OTel 只当导出格式** |
| L2 记录 | 记录有没有被改 | RFC 8785（JCS）、RFC 6962（Merkle）、哈希链 | **自建，约 200 行** |
| L3 身份 | 是谁、代表谁 | SPIFFE/SPIRE、Keycloak、W3C DID | **不碰，留接口** |
| L4 签名与透明 | 谁签的、能不能公开验 | Sigstore、SCITT（RFC 9943）、C2PA | **不碰，留接口** |
| L5 脱敏 | 能不能给第三方看 | Microsoft Presidio、字段级承诺 | 可选依赖（1 个） |
| L6 策略 | 什么情况下必须拦 | OPA/Rego、Cedar | 可选，**别把判定塞进 Rego** |
| L7 检查执行 | 具体怎么验 | semgrep、Great Expectations、pytest | 按场景选 1 个 |
| L8 决策 | **该验多少、花多少钱、债怎么记** | **没有** | **自建，本产品全部价值所在** |

前七层的问题都已经被认真回答过；第八层没有。这不是遗漏，是因为前七层都是"让事情可被观察"，第八层是"在稀缺下做选择"——后者需要业务约束（预算、人工、追责），学术界和开源社区都还没有这种约束的定义。

---

## 2. 逐层选型说明

### L1 采集：不要双写

openJiuwen 的 **Rail** 已经在 `ℋ_invoke / ℋ_call / ℋ_task` 上暴露生命周期钩子，带优先级与可见性门控。这意味着 L1 不需要引入 Langfuse/Phoenix 这类可观测平台。

**做法**：Rail 采集 → 内部事件流 → 需要外部消费时再导出 OTel 格式。
**理由**：双写会带来两份真相（时间戳、归属、采样率都可能不一致），审计场景最忌讳这个。
**代价**：放弃 Langfuse 现成的 UI。可接受——我们的 UI 要展示的是"等级与债务"，不是"调用瀑布图"。

### L2 记录：200 行就够

`record_hash = sha256(JCS(record 去掉 batch))`，`prev_hash` 串联。JCS（RFC 8785）可以手写 60 行，Merkle 可选（32 天内不需要）。

**不做签名**：签名的价值建立在"有第三方要独立验证"的前提上，demo 阶段没有；做了也只是增加演示复杂度。留 `sig_alg` 字段即可。

### L3/L4 身份与透明：不要自建

- 身份：SPIFFE/SPIRE 是工作负载身份的事实标准；Keycloak 管人。自建身份体系是三个月起步的坑。
- 签名/透明：Sigstore（签名 + 透明日志）、SCITT（RFC 9943，AAT 草案里明确引用为外部锚点）。
- **决策**：只定义接口（`principal`、`signer_kid`、`anchor`），实现留空。答辩时可以说"接口已按 AAT 草案字段预留"，而不是"我们实现了签名"。

### L5 脱敏：可选，别自己写 PII 规则

Presidio 覆盖了姓名/电话/证件/银行卡等常见实体识别。自写正则会在演示里翻车（漏一个身份证号就是合规事故）。

**决策**：若 demo 数据本身是合成的，可不引入；若要演示"给第三方看"，引入 Presidio 做一层，成本约 1 人日。

### L6 策略：OPA 能管"要不要拦"，管不了"值不值得验"

OPA/Rego 适合写准入规则（谁能调哪个工具、什么动作要人工）。但它不适合表达"这条 claim 的 cross_source 值 3.2 CU、能降 35% 风险"——那是数值优化，不是策略判定。

**决策**：准入类用 OPA（可选），调度类自建。**别把调度逻辑写成 Rego**，会变成不可调试的字符串。

### L7 检查执行：按场景选一个，不要造轮子

- 代码类：semgrep（规则化静态检查，成熟）
- 数据类：Great Expectations（数据质量断言）
- 通用：pytest 风格的断言 + 回源重算（自写）

**决策**：demo 的两个场景各选一个，其余不引入。

### L8 决策：空手起家，也正因为如此才值得做

这一层没有开源件，也没有论文。原因很实际：**它需要三样东西同时具备**——真实调用成本、业务严重度、人工预算。学术界拿不到后两样，开源社区没人有动机做。

## 3. 还缺什么：五个真实缺口

| # | 缺口 | 现状 | 为什么没人做 | 我们能不能做 |
|---|---|---|---|---|
| G1 | 检查的**价格** | 论文只报开销占比（ClaimReceipt 报 0.021%），没人把成本当决策变量 | 需要真实运行数据 | 能，Rail 白送 |
| G2 | **预算约束下的调度** | VeriHarness 全验、SSEG 粗粒度门控、OpenFC 学策略（事实核查域） | 需要业务约束定义 | 能，三条可解释策略 |
| G3 | **验证债务**（未验/过期/结构不可验） | 无人度量"结构不可验率" | 需要跨 Skill 语料 | 能，但要真去编译规则 |
| G4 | **规则→检查的编译** | 所有工作假定检查已存在 | 是脏活，且失败率高 | 能，作为窄路 A |
| G5 | **跨组织双向证据交换** | ClaimReceipt 单侧披露、agent-saga 单执行证明 | 需要两个组织 | 只能做接口，做不了闭环 |

**这五个里，G1–G3 是产品的核心，G4–G5 是延展。** 完整产品需要五个都覆盖，但 32 天只做 G1–G3。

## 4. 自建边界：三分法

判断标准只有一句：**能被一个成熟库替换的代码，一行都不要写。**

### 必须借（自建 = 负价值）

| 能力 | 借用 | 自建代价 |
|---|---|---|
| 追踪/事件 | Rail + OTel 导出 | 2 周，且永远追不上 |
| PII 识别 | Presidio | 3 周，且漏检风险高 |
| 准入策略 | OPA | 2 周 |
| 签名/透明日志 | Sigstore / SCITT 接口 | 1 个月起 |
| 静态代码检查 | semgrep | 1 个月起 |
| 前端框架 | Vue 或 React | — |

### 必须自建（借不到）

| 能力 | 为什么借不到 | 人日 |
|---|---|---|
| 成本模型与定价 | 依赖你的 Rail 与你的检查目录 | 4 |
| 严重度与风险先验 | 依赖你的 Skill 语义 | 2 |
| 三策略调度器 | 无人实现 | 5 |
| 等级语义与可归因记录 | 无人定义"等级 + 预算"的组合 | 3 |
| 债务台账 | 无人做三类划分 | 3 |
| 保证-成本曲线 | 无人做 | 2 |
| Studio 一屏 | 平台特有 | 4 |
| 证据包（计量底座） | 简版即可 | 4 |
| **合计** | | **27** |

### 绝对不碰

- 身份体系、PKI、透明日志运营
- 通用 Agent 框架（用 openJiuwen）
- 通用可观测平台（用 Rail）
- 通用数据质量平台（用 GX/semgrep）
- 自研 LLM 或微调

## 5. 我们自主做的工作，重要吗

**重要，但重要性有严格的前提。** 分三层论证，最后给一条反证。

### 5.1 不可替代性：缺口只在这一层

前七层每一层都能找到一个成熟件替代我们；**第八层没有任何替代品**。所以"自建 L8"不是重复劳动，是唯一没有替代品的位置。反过来说：如果我们去写 L1–L7 的任何一层，那部分工作就是可以删掉的。

### 5.2 评分口径：比赛只认这一层

DEMO 评审的四个维度里，"技术难度"和"商业价值"在这一层才成立：

- 技术难度：预算约束下的在线调度、债务分类、曲线复现——都能被追问三层；
- 商业价值：**"每元保证"是企业唯一会掏钱的数字**，而它只能从这一层出来；
- 用户体验：等级徽章 + 一句人话解释 + 一条曲线，比一堆 trace 图更接近决策者的使用方式。

而"我们又做了一个日志格式"在四个维度上都不占优。

### 5.3 资产属性：只有这一层会变厚

| 产物 | 三个月后 |
|---|---|
| 采集/记录代码 | 平台一升级就重写 |
| 签名/透明日志 | 换库就没了 |
| **成本基线（200 次真实调用）** | **越用越准** |
| **债务基线（每 Skill 的不可验率）** | **每接一个 Skill 增一条** |
| **策略库与失败模式** | **每次翻车增一条** |

只有第三行以下是资产，前两行是负债（要跟着平台改）。

### 5.4 一条反证（诚实版）

如果 32 天后我们做出的东西，**能被一个成熟库加 3 天配置替换**，那这份自主工作就不重要，而且有害——它消耗了唯一的时间预算。

判断方法很粗暴：把每个模块问一遍"有没有现成轮子"。有的，删掉；没有的，才是产品。

按这个标准，PRD 里的 27 人日里，约 **19 人日**是不可替换的（调度、债务、曲线、等级、定价），另外 8 人日（证据包、Studio）是"必须做但不构成差异"的承载物。

## 6. 依赖与合规（比赛硬约束）

| 项 | 规定 | 我们的做法 |
|---|---|---|
| 第三方代码 ≤30% | 按"作品有效代码量"计 | 依赖不 vendor、不复制源码；自写约 4000 行，依赖仅作库调用 |
| 开源许可 | 仓库 Apache-2.0 | 只用 MIT/Apache/BSD；**避开 AGPL**（Presidio 是 MIT，semgrep 是 LGPL，注意动态链接说明） |
| 依赖声明 | 名称/版本/来源/许可证/作用/占比 | 用 CycloneDX 生成 SBOM，随仓库提供 |
| 数据合规 | 演示数据须脱敏模拟 | 全部合成；附生成脚本与分布对照 |

**一个容易踩的坑**：semgrep 是 LGPL-2.1。作为独立进程调用（CLI）没问题；如果把它的库链接进主程序，需要在声明里写清。最稳的做法是**只作为外部命令调用**。

## 7. 32 天最小依赖集（建议 5 个以内）

| # | 依赖 | 用途 | 必需性 |
|---|---|---|---|
| 1 | openJiuwen（Rail / Studio / Skill） | 平台底座 | 必需 |
| 2 | Python 标准库（hashlib/json/uuid） | JCS、哈希链、ID | 必需 |
| 3 | 一个前端框架（Vue 或 React，二选一） | 面板 | 必需 |
| 4 | semgrep | 代码类检查 | 可选（副场景） |
| 5 | Presidio | 脱敏演示 | 可选（有余力） |

**不引入**：Langfuse、Phoenix、OPA、Sigstore、SPIRE、GX、DuckDB。理由统一：它们解决的是 L1–L7，而那些层我们要么有 Rail，要么演示阶段不需要。

---

## 8. 结论

1. **一个完整的可信/可审计产品，80% 可以由成熟开源件拼出来**——采集、身份、签名、脱敏、策略、检查执行都有标准答案。
2. **缺的 20% 全在决策层**：定价、调度、债务、曲线。这四项没有开源件，也没有论文，因为学术界拿不到业务约束。
3. **我们自主做的工作重要，但只在那 19 人日里重要**。其余 8 人日是承载物，做完就该收手，不要美化。
4. **判断标准一句话**：能被库替换的代码，一行都不要写；换不掉的，才是这个产品。

---

## 附：一句话答"为什么不自建底层"

> 底层每一个问题都有一个比我更强的团队在做，且是开源的；我重复它，最好的结果是追平。
> 决策层没有人做，因为它需要成本数据、业务严重度和人工预算——这三样只有真正跑在平台上的团队才有。
