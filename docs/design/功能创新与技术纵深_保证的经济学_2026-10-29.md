# 功能级创新与技术纵深：从「证据层」上移到「保证的经济学」

> 日期：2026-10-29
> 前提：不接受"改说法"当创新。本文只讨论**新功能、新目标、可积累的技术纵深**。
> 结论先说：**证据层已经被 90 天内的六篇工作铺满了，继续在那一层做功能创新没有空间。唯一还开着的门，是"验证要花多少钱、该验多少、债怎么还"——也就是把目标从"可审计"换成"可负担的保证"。**

---

## 0. 一个必须先接受的事实

过去 90 天，Agent 验证这条线上，**每个月都有人把一层功能拿走**。这不是文献综述，是"哪些门已经关了"的清单：

| 日期 | 工作 | 它拿走了什么功能 |
|---|---|---|
| 2026-08-18 | Artifact-centered Claim-aware Observability（arXiv:2608.18312） | 审计对象的最小结构：稳定 ID、kind、payload hash、creator、timestamp、status |
| 2026-08-19 | LEDGER（arXiv:2608.18398） | claim → evidence 的图，以及"给人审阅"的交互 |
| 2026-09-01 | Agent Flight Recorder（arXiv:2609.01931） | 防篡改的成本：48µs/事件、512B、$2.30/10 万事件、四类篡改 100% 检出 |
| 2026-09-02 | ClaimReceipt（arXiv:2609.01992） | **per-claim 回执**：PASS / INVALID / INCONCLUSIVE、充分性（sufficiency）、覆盖（coverage）、字段组消融、对审计方的选择性披露、0.021% 时间开销 |
| 2026-09-03 / 09-26 | SSEG（arXiv:2609.29703 v1/v2） | 不确定性的**传播**、隐藏脆弱路径的**定位**、发布门控（452/660 → 8/660） |
| 2026-10-01 | VeriHarness（arXiv:2610.00972） | 检查式验证：verifier 带 workspace + evidence tools + 可复用验证技能，且技能可从失败中自改进 |
| 2026-10-01 | Verify Claims, Not Scores（arXiv:2610.01348） | **四态裁决**（supported / unsupported / unresolved / not evaluated）+ "结论成立的边界" + 组件级价值定位 + 对 verifier 本身的体检（能被绕过） |
| 2026-10-26 | draft-sharif-agent-audit-trail-09 | 记录格式：pre-execution 记录、recording independence、trust-level 降级可归因、Decision Reproducibility、§13.8 Decision Margin |

把这些排在一起看，性质很清楚：

- **"给结论配证据"**——LEDGER 做了；
- **"给证据配回执、判三态或四态"**——ClaimReceipt 与 2610.01348 做了，而且都带"边界/充分性/覆盖"；
- **"把不确定性往前传播、定位脆弱路径"**——SSEG 做了，还带治理门控；
- **"验证器自己能验证"**——VeriHarness 做了；
- **"回执不可篡改、可被第三方验"**——AFT 给了成本，AAT 给了格式；
- **"回执能选择性披露给审计方"**——ClaimReceipt 已经做了（私密证据加密给 auditor）。

**旧稿想做的每一件事，现在都能指向一篇具体论文。** 这不是叙事问题，是功能清单已经被填满。

## 1. 门关完之后，还剩下什么

把上面八件工作放到一张"验证流水线"上看，它们覆盖的是**中间四段**：

```
观测 → 记录 → 保真 → 判定 → 回执 → ？→ ？
       LEDGER  AFT   SSEG  ClaimReceipt
               AAT        2610.01348
```

两端是空的：

**左端（上游）**：检查是从哪来的？
六篇工作全部**假定检查已存在**。没人回答"一个 Skill 的自然语言规则，怎么变成一条可执行的检查；编不出来的那部分怎么办"。这是规则可编译性问题——但它是"元层"，演示起来不直观，且容易变成 LLM 抽规则的花活。

**右端（下游）**：谁来决定验多少？
六篇工作全部**假定验证是免费且无限的**。VeriHarness 全验，SSEG 全门控，ClaimReceipt 全留回执。没有一篇处理真实组织里的约束：**验证要花 token、花延迟、花人工；预算有限；不是每条结论都值得验；验过的会过期；有些结论在结构上根本验不了。**

这就是唯一还开着、且**在 32 天内能用真实数据做出结论**的门：

> **不是"怎么验证"，是"验证这件事怎么被负担、被调度、被记账"。**

它的目标是新的：从 **auditability（可审计）** 变成 **affordability of assurance（保证的可负担性）**。

---

## 2. 目标创新：把"保证"变成一个有价格、有预算、有负债的东西

| 旧目标 | 新目标 | 判据（可当场测） |
|---|---|---|
| 每个结论可审计 | 每个结论有一个**保证等级**，且在给定预算下最优 | 同一预算下，风险加权漏检率低于基线 |
| 不确定性被标记 | 不确定性被**定价**（知道它要花多少才能消掉） | 每个缺口有报价：token/延迟/人工分钟 |
| 证据链完整 | **验证债务**可度量、可按期偿还 | 债务台账：未验/过期/结构不可验三类计数 |

为什么这是"目标级"而不是"功能级"的改动：它改了系统要优化的量。旧系统优化"证据的完整性"（越大越好），新系统优化"单位成本买到的保证"（有最优解，不是越大越好）。**一旦目标变成带约束的最优化，功能就自然是新的，而且能被量化比较**——这正是竞赛评分里"技术难度 + 商业价值"唯一能同时拿分的形态。

---

## 3. 功能创新：四个动词

四个动词构成闭环，缺一个都不成立。

### F1 定价：给每一次检查标价

**输入**：一条 claim 的证据包（哪些检查能做）+ Rail 实测的调用成本。
**输出**：每个可选检查的 `cost = {tokens, latency_ms, human_min}` 与 `effect = 预期风险下降`。

成本从哪来：Rail 的 ℋ_call 上本来就有 token 数与耗时，这是**平台白送的数据**；人工分钟从复核台账估。effect 从历史数据估（同类检查过去消掉了多少误判），冷启动用严重度 × 当前不确定度做先验。

**为什么别人没有**：所有论文的成本都以"更小更好"的形式出现（ClaimReceipt 报 0.021% 开销），没有人把成本作为**决策变量**建模。

### F2 调度：在线决定验、缓、认

**输入**：实时流 + 预算（每分钟 token、p99 延迟、每日人工分钟）。
**输出**：每条 claim 一个动作 `verify_now | defer | accept_with_grade`。

策略先做三条可解释的（不碰 RL）：
1. `always`（基线，VeriHarness 式）
2. `risk_gate`（只验高严重度）——SSEG 式的粗粒度版本
3. `budgeted`（拉格朗日：按 effect/cost 排序，预算耗尽即停）

**深度不在策略本身，在约束**：`accept_with_grade` 必须写出"我接受它，保证等级 B，理由是预算耗尽且该 claim 的影响面为 X"。这句话是可以被审计的，而"没验"在现有系统里是**不可见**的。

### F3 记账：验证债务台账

三类债，性质不同，处理方式也不同：

| 债的类型 | 定义 | 为什么重要 |
|---|---|---|
| 未验证 | 有检查、没跑 | 可偿还（花钱） |
| 已过期 | 验过，但输入已变 | 可偿还（重跑） |
| **结构上不可验** | 规则无法编译成检查，或缺必填证据 | **不可偿还**，只能改 Skill |

第三类是杀手：它把"审计"变成"设计审查"。一个数字——**某 Skill 有 63% 的结论在结构上不可验证**——比任何回执都有说服力，而且只有做了编译尝试才能得出。

### F4 偿还：预算增量的边际收益

**输入**：当前预算 + 债务台账。
**输出**：一条曲线——预算 +10% / +50% / ×2 分别能买回多少保证；以及"再花多少钱也买不回来"的那部分（结构不可验）。

**这是整个方案最像产品的一屏**：它回答的是企业真正会问的问题——"我要为可审计性付多少钱，付了能换到什么"。现有工作没有一条曲线，因为它们没有价格。

## 4. 技术纵深：四个难点，每个都能被追问三层

| 层 | 难点 | 为什么难 | 32 天内能做到什么 |
|---|---|---|---|
| 成本模型 | 检查成本依赖上下文（上下文越长越贵、工具越慢越贵） | 不能用常数，要按调用类型回归 | 用 Rail 实测 200 次调用，拟合一个分段模型 |
| 风险估计 | 没有标注，哪来的"漏检风险" | 冷启动只有先验；一旦有人工复核就能校准 | 严重度 × 不确定度先验 + 20 条人工标注校准 |
| 在线调度 | 预算约束下的选择是背包问题，且要低延迟 | 精确解太慢，要可解释的近似 | 贪心 + 阈值，p99 开销 < 5ms |
| 帕累托前沿 | 要证明"同一预算下更优" | 需要基线对照与统计 | 2 个 Skill × 200 claim × 3 策略，画 3 条曲线 |

**能被追问的三层**（提前准备）：
1. "你的成本模型准吗？" → 给拟合残差，并说明误差如何影响调度（敏感性分析）。
2. "风险是先验，凭什么信？" → 给 20 条人工标注的校准曲线，承认样本小，给置信区间。
3. "这和'少验一点'有什么区别？" → 区别是**可归因**：每一条"没验"都有等级、理由和预算账；`always` 策略下你根本不知道漏了什么。

## 5. 技术壁垒：三样会自己变厚的东西

| 资产 | 为什么别人补不上 | 增长速度 |
|---|---|---|
| **成本基线**（每类检查的真实 token/延迟/人工分钟） | 只有跑在真实 Rail 上才有的数据；论文里的数字是别人的系统 | 每次运行都在增长 |
| **策略库 + 债务基线**（每个 Skill 的债务结构） | 绑定具体 Skill 的规则形态；换生态就得重测 | 每接一个 Skill 增一条 |
| **"结构不可验"的判定规则**（哪类规则编不出来） | 需要真的试过编译，失败模式是经验 | 每次失败增一条 |

**不要说"我们有壁垒"，要说"这是我们攒了 200 次调用和 40 条编译失败记录的地方"。** 前者空，后者可查。

诚实的边界：32 天内这三样都只是**种子**，样本量小到不能称"壁垒"，但足够证明"它会随时间变厚"——而这是壁垒唯一诚实的定义。

## 6. 发展性：三阶段，每段挂一个外部日期

| 阶段 | 时间 | 做什么 | 外部锚点（可核对） |
|---|---|---|---|
| P1 | 32 天（11-25 → 12-27） | 定价 + 三策略 + 债务台账 + 一条帕累托曲线（2 Skill × 200 claim） | 大赛 DEMO 截止 12-27 |
| P2 | 3–6 个月 | 策略库扩展到 5 类检查；债务基线覆盖 Hub 上 20 个 Skill；把"结构不可验率"做成 Skill 上架前的一项体检 | AAT 草案每两月一版（-09 是 10-26），字段会继续演化 |
| P3 | 12 个月 | "保证等级"成为生态里的可比指标：Skill Hub 显示每个 Skill 的 assurance profile；企业采购用"每元保证"做横评 | EU 2026/1744 的 Annex III 义务 2027-12-02 生效，采购侧开始要这类数字 |

P3 才是真正的壁垒位置：**当所有人都在报"我验了什么"，只有你在报"我花了多少、买到多少"。** 指标一旦被采用，迁移成本就出现了。

## 7. 32 天切片：做什么、明确不做什么

**做**（按人日）：
- 成本采集（Rail 埋点 + 拟合）：4
- 风险先验 + 20 条人工标注：2
- 三策略调度器（always / risk_gate / budgeted）：5
- 债务台账（三类债 + 聚合视图）：3
- 帕累托曲线 + Studio 一屏：4
- 证据包 + `verify`（沿用 v2 方案，仅作为"计量单位"存在）：4
- 视频 + 报告 + PPT：5
合计 ≈ 27 人日，3 人可覆盖。

**不做**：
- 不做新的裁决算法（SSEG / 2610.01348 已占）；
- 不做新的回执格式（ClaimReceipt 已占）；
- 不做防篡改（AFT 已商品化，直接用哈希链即可）；
- 不做选择性披露（ClaimReceipt / agent-saga 已有，最多引用）；
- 不做 RL 调度（OpenFC 已在做"学验证策略"，32 天内比不过，也没必要）。

**关键取舍**：证据包从"交付物"降级为"计量仪表"。代码量减少约 30%，但目标的层级上去了。

## 8. 如果你不想换轴：两条窄路

换轴有风险（评委可能觉得"这不是证据链了"）。若坚持留在证据层，只剩两条**窄但真实**的缝：

**窄路 A：规则可编译性审计（左端）**
不验证结论，验证"这个 Skill 的规则能不能被验证"。产出：可编译率、缺字段清单、主观条款清单、每条编译规则的 fixture（正例/反例）。价值主张："你买的这个 Skill，有 40% 的结论在结构上无法被审计。"——这是**生态级**的度量，只有拿到 Skill 语料的人能做。缺点是演示不直观，要把"编译"过程做成可视化才有说服力。

**窄路 B：跨组织证据交换（右端）**
一方出结论、另一方出审计，双方都不想暴露原始数据。产出：可脱敏、可验、带责任链的证据包交换协议（字段级承诺 + 选择性披露 + 责任主体签名）。ClaimReceipt 做了单侧披露，没做**双向交换与责任划分**。缺点是与"32 天 demo"的匹配度一般，因为需要两个组织。

两条都可以做，但都只够撑一个功能，撑不起一个 32 天的作品。**这也是我建议换轴的实际理由，不是审美偏好。**

## 9. 风险与答辩口径

| 风险 | 概率 | 应对 |
|---|---|---|
| 评委认为"这只是加了个预算" | 中高 | 演示必须给**对照曲线**：同一预算下漏检率 22% → 9%；并展示 `accept_with_grade` 的可归因文本 |
| 风险先验被质疑 | 高 | 给校准曲线 + 承认样本小 + 给敏感性分析 |
| 成本数据样本太少 | 中 | 用 200 次真实调用，公开原始数据表 |
| "结构不可验"判定不准 | 中 | 只报"我们试过编译且失败"的类别，不推断未试过的 |

**答辩三句**：
1. "别人在回答'这条结论有没有证据'，我们在回答'知道这件事值多少钱'。"
2. "同一条预算，我们的调度把风险加权漏检率从 22% 降到 9%，而且每一条没验的结论都有等级和理由。"
3. "这个 Skill 有 63% 的结论在结构上不可验证——这个数字，只有真的去编译过规则的人才知道。"

## 10. 一句话总括

**证据层已经商品化，价值必然从"产出证据"上移到"分配保证"。**
把旧稿的证据包留着，但改它的身份：不是交付物，是仪表盘。然后用它去回答一个没人回答过的问题——**知道这件事，要花多少钱**。
