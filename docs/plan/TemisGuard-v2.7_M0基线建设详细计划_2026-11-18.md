# TemisGuard v2.7 M0 基线建设详细开发计划

版本：v1.0 / 2026-11-18。适用：四人团队，无固定日历截止时间。
依据：PRD-v2.7、完整开发方案 2026-11-18、工程目录与整理记录。
本文件是实施计划，所有目标尚须提供运行证据，不能当成已通过报告。

## 1 M0 要解决的问题

建立一个可安装、可测试、可复现、单一源码入口的工程底座，证明三框架能够经过同一个受控执行边界，为 M1 契约与 SQLite 账本开发提供可靠起点。

M0 不承诺完整 Gate、生产审批、SQLite 账本、不确定性债务及八项读数已经实现。最小 spike 使用测试策略和审批驱动验证控制位置，不冒充正式产品。

### 已知起点

- 根目录已合并后端，原工程和16个差异冲突保留在 archive/workspace-20261118。
- 103个 Python 文件已通过 AST 静态语法检查，归档哈希复核无差异；这不等于运行测试通过。
- 当前系统 Python 3.14.3 未安装 pytest；实际 SDK 支持的 Python 版本尚未验证。
- pyproject、requirements、rail/requirements-demo 存在重复依赖口径；后者仍锁 openjiuwen==0.1.18，与 PRD 的0.1.20.post1冲突。
- 新 v2.7 包仅有骨架。现有 CI 只调用前端 npm run verify，后端和三框架验证未纳入。
- 历史539条用例仅为历史参考；本次应以实际收集的唯一用例清单为准。

## 3 任务分解与责任

### T0.1 工程盘点与冲突审查（A主责，C复核）

输入：归档manifest、活跃源码、原根源码、嵌套原源码及Git已有改动。

步骤：

1. 导出活跃文件清单、文件大小、SHA256及目录角色，排除依赖缓存。
2. 审查16项冲突，每项记录接口差异、行为差异、选版理由、测试证据及是否需要回补。
3. 比对归档tests/fixtures测试与活跃测试，列出原测试入口；检查CLI、Makefile、CI、conftest导入路径。
4. 对项目模块记录__file__，从根目录及根外工作目录分别验证安装导入，禁止依赖旧目录或意外cwd。
5. 完善README中的安装、目录、旧语义保留说明；保留用户已有变更。

交付：docs/reviews/baseline/inventory.md、conflict-review.md、test-inventory.json、import-origins.json。
退出：16/16冲突审完；归档校验100%；所有活跃入口仅指向根工程；未知用途文件有明确保留说明。

### T0.2 依赖与运行环境（A主责，B配合，D复核）

步骤：

1. 验证Python候选版本与SDK安装兼容性，不沿用系统3.14作为默认结论。
2. openJiuwen固定0.1.20.post1；另外两框架查官方资料并用安装/运行验证选择精确版本。
3. 选择一个依赖声明源；pyproject描述核心及可选组，锁文件记录完整传递依赖。requirements由同一源生成或明确标注用途，删除活跃的相互矛盾版本约束前保留差异记录。
4. SDK可共存则一个主环境；不可共存则拆分core、jiuwen、langgraph、agents环境，并给出统一受控执行协议与各自锁文件。隔离不得成为各框架另写一套Gate的理由。
5. 提供PowerShell bootstrap/verify脚本，显式使用环境解释器，命令失败返回非零；安装过程不修改系统Python。
6. npm以package-lock执行npm ci，记录Node/npm精确版本；核验现有锁文件可安装性。
7. 从空环境完整重建两次，执行pip check及版本指纹比较。

交付：锁文件、环境矩阵、scripts/bootstrap.ps1、环境报告和.env.example（仅变量名/假值）。
退出：每个必需环境2/2重建成功；pip check零冲突；无隐含全局依赖。存在依赖冲突时必须有可运行隔离方案，不能仅记风险后宣布完成。

### T0.3 后端真实测试基线（C主责，A复核）

步骤：

1. 在正确环境执行collect-only，保存nodeid及总数N，固定tests和fixtures的发现范围。
2. 对每个skip/xfail建立原因清单；网络、模型、平台限制用显式marker分组。
3. 首次完整运行保存passed/failed/error/skipped/xfail与JUnit；逐失败归因到依赖、导入、测试缺陷或业务缺陷。
4. 修复与基线恢复直接相关的问题；涉及业务语义变更先加能复现缺陷的用例，不为了全绿修改预期、减弱断言或删测试。
5. 离线测试在不提供模型密钥时执行，禁止测试意外联网；生成基线耗时与最慢用例列表。
6. 相同锁文件、相同夹具连续跑3轮；各轮用例集合完全一致，结果均通过。

交付：collect.json、junit.xml、failure-triage.md、skip-register.md、三轮汇总。
退出：冻结离线用例N条全部通过、收集错误0、未经登记skip/xfail0，三轮不稳定失败0。若N不同于历史539，必须给出差异清单，不强行凑数。

### T0.4 三框架控制可行性spike（B主责，A/D复核）

目标：验证工具执行前可控制的位置和异常/恢复语义，不依赖日志回调推断成功。

框架真实实例必须经过同一测试版guarded_call；测试策略可直接指定ALLOW/ASK/DENY/REWRITE；人工应答可用测试驱动，不要求M0已具备Web审批。未通过原生钩子控制则工具包装接入；必须说明哪些内置工具未覆盖。

|编号|每框架场景|观测与通过线|
|---|---|---|
|S01|ALLOW|工具实际执行1次，结果捕获1次|
|S02|DENY|文件/调用计数均证明执行0次，拒绝记录1次|
|S03|REWRITE|仅执行改写后参数1次，原参数执行0次|
|S04|ASK批准|批准前执行0次，批准后执行1次|
|S05|ASK拒绝|执行0次，拒绝终态1次|
|S06|ASK超时|高危执行0次；超时可用短测试时钟，证明同一状态逻辑|
|S07|工具异常|实际调用1次，异常终态1次，无重复回调记录|
|S08|等待时取消|取消后执行0次，取消终态唯一|
|S09|并行上下文|10个任务并发，run/task/args关联错误0|
|S10|中断resume|同一业务task恢复，run_id不变、segment按约定递增|
|S11|父子委派|各自run_id可区分，父子关系可查，无子结果误归父级|
|S12|未注册副作用|测试工具明确side_effect=true却未分类，UNHOOKED可见且不重复|

每个场景每框架重复3次；每轮使用新临时工作目录；输出108条执行结果及SDK版本。并发场景每轮10任务，分别校验身份。spike可用内存测试事件，不声称已证明数据库持久性。

另做每框架3次真实模型冒烟：模型发起受控文件写工具，文件只写测试目录；保存脱敏调用摘要、模型标识、实际工具副作用和结果。模型仅直接返回文本或只调用stub不算通过。在线失败明确区分凭据/网络/模型/SDK，不能降级mock后标绿。

交付：tests/spikes/或scripts/spikes/可重复入口、adapter-capability-matrix.md、运行结果JSON、模型冒烟报告。
退出：36/36场景通过、108/108执行通过、在线9/9通过；列出未覆盖框架内置工具及后续接入方式。框架内绕过工具不得被宣称已覆盖。

### T0.5 前端与本机运行入口（D主责，B复核）

步骤：

1. npm ci后运行现有npm run verify，涵盖类型、lint、契约、单测、构建、预算、E2E、视觉及可访问性。
2. 记录现有页面/场景数量及API端点实际结果；旧ARS功能按历史基线核验，不要求此阶段升级为八项读数。
3. 记录mock和api模式支持状态；缺端点404明确列入缺口，除非修复真实后端，不能以mock替代称api已完成。
4. 建立本机启动/停止脚本，管理自身PID、端口冲突和健康检查；服务绑定127.0.0.1，停止只作用于本脚本启动的进程。
5. 现有后端若缺健康端点，增加最小探活并写明语义：只证明服务进程就绪，不证明v2.7功能完成。
6. 连续启动/检查/停止3轮，保留退出码和健康结果。

交付：前端验证报告、endpoint-baseline.md、scripts/start-dev.ps1、stop-dev.ps1、本机操作说明。
退出：既有verify全绿；启动健康3/3、停止成功3/3、遗留自身进程0；无未解释的视觉差异或用例减少。新增的v2.7页面留在M4。

### T0.6 CI与证据打包（C/D主责，A终审）

步骤：

1. 扩展现有UI流水线，新增core离线回归和三框架spike矩阵，锁定Python/Node与依赖。
2. 普通CI不依赖真实模型密钥；在线任务手动或受凭据控制触发，缺凭据显示未运行，不能当通过。
3. 测试失败仍上传JUnit、脱敏日志、版本指纹；报告不上传.env、数据库原始敏感内容及模型凭据。
4. 建立baseline-summary.json，字段至少含源码指纹、锁文件指纹、环境、用例数、失败数、skip原因、框架矩阵、在线状态及各证据路径。
5. 从干净环境按README重跑全套，将结果与当前环境比较。

交付：CI配置、scripts/verify-baseline.ps1、报告生成器、M0验收报告。
退出：必需CI任务全部通过；故意制造一个断言失败时CI确实失败并保留报告；恢复后全绿；所有退出条件都能定位到证据。

## 4 执行顺序与四人协作

1. A/C先完成T0.1并冻结用例清单；B并行核查SDK和控制点；D盘点前端与运行入口。
2. A/B完成T0.2环境及锁定，作为T0.3、T0.4真实运行前置。
3. C恢复测试基线；B完成三框架spike；D完成前端基线与脚本。
4. 四人共同审查差异、能力矩阵和失败归因，再执行T0.6。
5. A汇总M0退出清单；C核验数字，B核验真实副作用证据，D核验从零启动步骤。

共享文件pyproject/锁文件由A统一修改；CI由D统一整合；测试清单由C维护；适配器接口由B提出、A评审。每个交付物必须有至少一位非作者复核。

## 5 性能与质量度量边界

M0记录数据，不提前强制未来功能的性能达标：

- 记录安装耗时、测试总时长、峰值并发、CPU/内存、磁盘及三框架调用开销。
- spike额外开销拆分框架、测试门控与工具本身；ASK等待单独计时，模型时延不计作规则时延。
- Gate P95<50ms和SQLite两段写P95≤5ms分别在M2/M1正式实现后验收，M0不能用空函数证明达标。
- 不对旧工程追求任意全局覆盖率百分比。新基线脚本应验证成功、失败退出、路径错误、环境缺失四类行为；三框架覆盖按上述场景矩阵计数。
- 不新增无依据的测试数量目标；新增用例必须对应一个风险或验收行为，禁止重复断言凑数。

## 6 缺陷分级与退出规则

|等级|示例|M0处置|
|---|---|---|
|阻断|DENY仍执行、串任务、安装失败、原文件丢失、秘密泄露|必须修复，禁止进入M1正式集成|
|严重|回归失败、SDK无法恢复、依赖不可重建、CI假绿|必须修复或给出同等保证的已验证替代实现|
|一般|历史页面文案过时、可定位的非核心展示缺口|登记到后续阶段，明确责任与验收，不掩盖现状|

未完成在线验证可继续做不依赖该结果的设计，但M0总状态为部分完成；任一框架控制验证失败不能声称三框架基线完成。

## 7 M0验收报告模板

- 总状态：PASS / PARTIAL / FAIL。
- 环境：OS、Python、Node、npm、模型提供商标识、SDK及全部锁文件摘要。
- 用例：collected、passed、failed、errors、skipped、xfail；与首次清单增减原因。
- 工程：冲突已审数量/16；归档完整率；导入路径检查结果。
- 三框架：36场景结果、108执行结果、9次模型冒烟结果及未覆盖工具。
- 前端：各verify子项、场景数、启动停止3轮结果。
- 重建：两次干净环境日志；离线回归三轮结果。
- CI：成功任务和失败注入验证证据。
- 未解决缺陷：等级、责任人、后续阶段、影响范围。
- 结论：是否允许进入M1；不能仅以“代码已提交”或“静态检查通过”给PASS。
