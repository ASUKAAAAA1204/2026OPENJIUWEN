# 增强清单：不受工期约束时还值得做什么

> 日期：2026-10-30
> 前提：假设人力和时间不是约束。判断标准三条——**让分数更真、让护城河更深、让决策更近。**
> 不满足这三条的一律进 §7「不值得做」。

---

## 1. 效度工程：把"自定指标"变成"可辩护的预测"

这是当前最大的短板，也是最值钱的投入。

| # | 做什么 | 方法 | 为什么值 |
|---|---|---|---|
| 1.1 | **真值集** | 200 条 claim，3 名审核员独立标注"审计时会不会被问倒"，多数票为标签；把 ARS 当预测变量，算 AUC / PR-AUC | 没有它，ARS 只是"定义良好的数"，不是"能预测审计失败的指标" |
| 1.2 | **分维信度** | 五个维度分别算 κ，不只算总分 | 找出哪一维最靠主观，决定要不要重定义 |
| 1.3 | **置信区间** | Bootstrap 1000 次，报 `46 [38, 54]` | 12 条样本就报整数 46，是假精度；区间才是诚实 |
| 1.4 | **数据驱动权重** | 用真值集做逻辑回归/排序学习，学出权重，与手拍 25/25/20/15/15 比 AUC | 权重拍定是最大质疑点，用数据回答 |
| 1.5 | **纵向效度** | 同一 Skill 多轮改造，看 ARS 上升是否对应"被问倒率下降" | 这是"提升闭环"成立与否的唯一证据 |

**目标线**：AUC ≥0.75；每维 κ ≥0.6；权重替换后 AUC 提升 ≥0.05 才换。

---

## 2. 对抗测试集：把"抗博弈"从规则变成证据

现在的抗博弈是几条检查，不成体系。

| # | 做什么 | 方法 |
|---|---|---|
| 2.1 | **红队 Skill 库** | 造 10 个"形式合规"Skill：补 locator 但不解析、拆规则成琐碎谓词、刷 digest、伪造 fixture、把 LLM 判定标成确定性 |
| 2.2 | **攻击成功率** | 每个红队 Skill 记录：ARS 被抬高多少、是否被标记 |
| 2.3 | **语义等价检测** | 规则拆分用 AST/逻辑等价判断，不靠人工抽检 |
| 2.4 | **声明-事实差** | `declared_evidence - resolved_evidence` 作为独立指标，公开在报告里 |

**目标线**：10 个红队样本中 ≥8 个被标记；形式合规样本的 ARS 增益被折减 ≥70%。

**价值**：这一套做出来，就是"我们的分数不能被刷"的证据，比任何论证都硬。

---

## 3. 开放口径与标准映射：从"我们定的"到"大家能算的"

| # | 做什么 | 为什么 |
|---|---|---|
| 3.1 | **开源 rubric + 参考实现** | rubric.md（定义 + 权重 + 边界）+ 约 200 行 reference implementation + golden files；任何人可复算 |
| 3.2 | **标准覆盖矩阵** | 与 AAT -09 的 13 个必填字段、EU AI Act Art.12 记录要素、SOC 2 / ISO 42001 控制项做覆盖对照，标明"覆盖/部分/不覆盖" |
| 3.3 | **导出适配器** | 证据包导出为 AAT 风格 JSONL、OTel 事件，让外部审计工具能消费 |
| 3.4 | **走平台规范流程** | 把 ARS 作为 openJiuwen 上架规范的**提案**提交（不是自称标准），争取生态位 |

**注意**：3.2 只能写"覆盖矩阵"，**不能写"合规"**——AAT 草案自己声明映射是 informative，不是合规评估。

---

## 4. 决策增强：从"一个分"到"一次发布决策"

| # | 做什么 | 场景 |
|---|---|---|
| 4.1 | **版本 diff** | 新版本 vs 上一版本，五维逐项对比；某维下降 >5 分触发回归告警 |
| 4.2 | **逆向规划** | 给定"月底前必须到 B 档"，反推最小改造集 + 排期 + 预算 |
| 4.3 | **三角色视图** | 审核员看结论、技术看路径、采购看对比——同一数据三种切法 |
| 4.4 | **人读凭证** | 一页可打印的"审计单"：结论、出处、缺口、签发人、校验码 |
| 4.5 | **发布说明草稿** | 自动生成"本次发布的可审计性变化"段落，直接进 release note |

**判断**：4.1 和 4.2 是发布流程真正会用的功能；4.3 决定产品能不能卖给三类人。

---

## 5. 架构升级：让"第三方复算"在结构上成立

| # | 做什么 | 为什么 |
|---|---|---|
| 5.1 | **独立验证者** | verifier 独立进程/独立代码库，只读 bundle，输出签名报告；与主判定分歧进仲裁队列 |
| 5.2 | **事实注册表** | `fact_id = hash(实体+属性+时间窗)`，跨 Skill 共享同一条事实与新鲜度 |
| 5.3 | **增量重算** | 依赖图 + 失效传播：输入变一点，只重算受影响子图 |
| 5.4 | **规则类型系统** | IR 支持 int/float/string/set/time + 区间语义，为"结论成立范围"铺路 |
| 5.5 | **可解释反事实** | 不只说"缺什么"，还说"补上后分数会到多少"（敏感性分析） |

**5.2 + 5.3 是规模化前提**：250 个 Skill 每天跑，不共享事实、不做增量，成本会线性爆炸。

---

## 6. 生态资产：让分数有相对意义

| # | 做什么 | 为什么 |
|---|---|---|
| 6.1 | **基线分布** | 按 Skill 类别给分位数："78 分 = 同类前 30%" |
| 6.2 | **fixture 众包** | Skill 作者提交 fixture，平台审核；fixture 数量成为生态指标 |
| 6.3 | **失败语料数据集** | 标准化 schema + 版本 + 统计口径，对外发布，建立引用 |
| 6.4 | **三级认证** | 自评 / 平台复核 / 第三方审计，对应不同信任级别与价格 |

**6.1 解决"78 分算好还是差"**——没有基线，任何分数都是绝对值，无法解释。

---

## 7. 不值得做（看着好，实际是坑）

| # | 想法 | 为什么不做 |
|---|---|---|
| 7.1 | 保险/担保模式（ARS 达标才保） | 需要精算数据与监管资质，32 天（甚至 3 年）都摸不到 |
| 7.2 | RL 学习调度 | 样本不足，学出来不可解释，反而毁掉"可复算" |
| 7.3 | 自研密码学 / 透明日志运营 | AFT/AAT/Sigstore 已商品化，重造是负价值 |
| 7.4 | 通用 Agent 框架 | 平台已提供，做了就是重复 |
| 7.5 | 给所有文件类型做适配器 | 收益递减，先做结构化与代码两类 |
| 7.6 | 追求 UI 精美 | 评分里"用户体验"只占一项，且拦截那一下比动效重要 |

---

## 8. 如果只能加三件

按"改变判断"的力度排序：

1. **效度工程（1.1 + 1.3）**——把"我们定的分"变成"能预测被问倒的分"，且给区间。
2. **红队测试集（2.1 + 2.2）**——把"抗博弈"从口号变成"10 个样本里 8 个被抓"。
3. **开放口径（3.1）**——rubric + 参考实现公开，让别人能算，才谈得上标准位。

三件加起来约 15–20 人日，但性质完全不同：**前两件让分数可信，第三件让分数可传播。**

---

## 9. 一句话

**不受工期约束时，最该做的不是更多功能，而是三件事：证明这个分数能预测审计失败、证明它不能被刷、证明别人能算出同一个数。**
**其余都是在这三件成立之后才有意义的装饰。**
