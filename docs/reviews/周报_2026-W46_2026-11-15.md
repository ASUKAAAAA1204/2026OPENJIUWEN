2. 完成两套代码基线的核查与判定
对根目录 src 与 2026OPENJIUWEN-main/src 做了 AST 级全量盘点，逐个模块核对类、函数与字段。结论：
2026OPENJIUWEN-main/src 共 48 个 Python 文件、8921 行，包含 verifier、resolver、evaluator、replay、ledger_verify、antigaming、ir_runtime 等完整实现，是唯一可信基线；
根目录 src 共 1449 行，模块集合是上述版本的子集，属早期精简快照；
嵌套 ui 目录只有 package.json 桩，前端以根目录 ui/ 为准。
据此形成"迁移嵌套版、删除旧 src、统一为单一代码目录"的收敛结论，纠正了此前按嵌套目录文档判断进度的偏差。

3. 完成测试基线实测与失败归因

三、本周形成的三条结论

第一，代码只有一份可信基线。两套 src 并存会导致测试路径、接口约定、文档引用指向不同版本，任何改动都可能"改了 A、跑的是 B"，必须先收敛再开发。

第二，失败用例不等于功能缺失。118 条失败与错误全部来自依赖，说明既有底座质量可用，修好依赖即可恢复可验证性，复用判断成立。

第三，v2.7 是能力范式切换而非版本迭代。从"离线批量打分评审"转为"执行前同步控制加追加式账本"，决策门、执行策略、读数、回放四处的对象与口径都要更换，不能靠打补丁实现。
