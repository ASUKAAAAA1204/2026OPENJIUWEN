B / C 回传要求与分批交接约定
交接修订：2026-11-01-return-v2（北京时间）

本文件与 B_HANDOFF.txt、C_HANDOFF.txt、COMMON_HANDOFF.txt 一起使用。角色任务、业务指标和现有代码限制仍以这些说明为准；本文件补齐“收到之后做什么、何时回传、回传哪些材料、A 如何继续”的操作要求。
return_templates/ 中的 JSON 是回传说明模板，不是已经冻结的业务接口，不改变 core/ 或 schemas/contracts.py。模板里的 null、空列表和 not_filled 表示尚未填写，绝不能当成实测为零或验收通过。

一、这轮怎样交接

A 将 B_交接包_20261101.zip 给 B，将 C_交接包_20261101.zip 给 C。两包各自带齐代码参考快照、原始数据、验收记录和说明。
B/C 可以直接用本地压缩包回传，不要求先上传 GitHub。未来提交 GitHub 的对象是全队集成并验收的项目；本次交接快照没有完整前端，也没有 Git 历史。
不整体覆盖自己的新代码。以原 MANIFEST.json、文件摘要和自己的当前版本对照后，在所属目录内修改。
保留一份原交接包作为只读基线，在另一工作副本开发。verify_files.py/run_offline.py 用于验证原交接基线；修改源码后原清单报告差异是正常现象。新代码用回传说明里的命令测试并生成新版本/摘要，不重写原清单来隐藏修改。
收到后先按 QUICKSTART.txt 运行文件校验和离线复查，保留结果。现有正式状态为 M5/M15 passed、M10 not_verified、overall partial；这不是网络错误。
开发时可并行；B 的规则格式必须先和 C 对齐，C 的正式 replay 要尽早返回 A。A 不需要等评分、界面、账本全做完才开始接入。

二、分四批回传，允许先交可运行的小版本

R0 接收确认：B/C 各自先回传。
  内容：收到的角色包、修订号和 MANIFEST.json 的 SHA-256；文件校验/离线复查结果；使用的 Python 与依赖版本；自己代码版本；发现的第一个阻塞；预计下一批交付时间（北京时间）。
  如果尚无 Git 提交号，提供改动文件清单及摘要即可，不编造提交号。
  接收失败时附具体输入、运行命令、退出码和脱敏错误，不只回复“运行不了”。

R1 最小可联调版本：这是 A 最先需要的一批。
  B 先和 C 对齐规则结构、版本、算子、变量/字段映射、claim-rule 关系和失败处理。
  B 同时给 C 可执行规则/编译结果，给 A 一份一致的规则快照及字段说明。至少一条真可执行规则及成立、反例、边界预期。
  C 返回正式 replay 的可运行代码、入口/依赖/replay_id，以及结论成立、被反驳、证据不足三个固定样例与预期输出。
  B/C 提交需要 A 补充的证据字段或接口问题，并给一个固定复现样例。
  A 收到后先跑小样例，接入正式 replay，检查删除证据是否改变业务结果；问题按目录交回对应负责人处理。

R2 扩大联调与正式核验结果。
  B 补齐真实编译成功/失败输出、失败语料与规则版本；C 补齐独立 verifier、双跑、新鲜度和引用证据记录。
  C 对每条 claim 说明正式判定、必要证据、规则/replay/verifier 版本和未完成原因，结果同步给 B；A 取得副本以核对最小包是否仍支持正式复核。
  A 用固定输入扩大到批量包，重做最小集与删除测试，保留完整包和新输出，返回联调报告及问题清单。
  本包的 100 条采集样本与 PRD 的 20 条演示基准分别记录，不能拼接分母或互相替代验收。

R3 实测成本与模块验收闭环。
  B 回传各改造动作的实际执行记录，C 回传正式核验、双跑、独立 verifier、账本及实际人工处理的记录。
  A 同时补测自己的 S3 回源/打包成本，并据真实操作样本拟合相应动作价格。
  B/C 各自返回本模块指标报告，标明通过/未验证/失败及依据；全队再验完整 M10/M11，不能用 A 的 S2 小计替代。
  B 的评分/方案结果和 C 的账本/闸门结果按职责继续给 D；A 收到与证据、成本有关的接口版本和联调结果。

时间安排：R0 优先完成；R1 是双方第一个开发交付，不等整块模块完成才返。具体日期由各负责人回填，COMMON_HANDOFF.txt 的 D0–D5 只是相对排期参考，不是已承诺截止日期或比赛官方时间。
如果缺一项，写明缺什么、影响哪一步、由谁补和预计时间。可以交 partial 批次，但不能把它标成模块全部完成。

三、B 必须回传给 A 的内容

B-1 正式规则快照和配套说明（R1 首批）。
  规则 ID/版本、原文、编译结果和可执行 IR、操作数/字段映射、claim 关联、依赖数据及来源要求。
  说明 C 已对齐到哪个规则/接口版本；没有对齐的项明确列 pending。
  附成立/反例/边界输入与预期；四种编译失败码样例随扩展版本补齐。
  A 将此作为证据中的正式规则快照，替换 A 的 pe_rule 样例；A 不代做 B 的编译器。

B-2 代码及运行入口。
  修改的 engine/ 文件或补丁、变更清单、可复现命令、必要依赖和实际输出。
  保留原仓库相对目录，列 base_sha256 与 returned_sha256；新增文件 base_sha256=null 并标明新增。
  涉及共享模型的修改先列接口变更请求，不把未经定版的 core/ 改动当作可以直接覆盖的文件。

B-3 动作实测记录（有结果就回传，R3 补齐）。
  区分 capture_claim、rewrite_rule、add_field、rerun_check 等实际发生的动作与方案预测，名称以双方版本约定为准。
  每条记录可追到运行、动作和 claim，附原始测量依据；具体字段见 RETURN_COST_FIELDS.txt。
  A 用于成本统计/拟合。A 现有 capture_claim 的估计误差不代表 B 的 M4 已通过。

B-4 接口问题、验收结果和未完成项。
  对 A 的数据有什么需求、缺哪个字段、哪条样例失败、期望与实际结果是什么。
  提供 M1/M3/M4/M14 等本模块指标的输入、运行命令与报告；没做的写 not_verified。
  评分/方案到 D 的最终 JSON 如涉及 A 数据，给 A 相同版本的样例以便复查。

四、C 必须回传给 A 的内容

C-1 正式 replay 的可运行代码（R1 最关键）。
  已有调用边界：replay(bundle_json: dict, payloads_json: dict) -> dict | None。
  提供实际导入路径、入口、依赖、replay_id、接受的规则版本和使用的证据字段。
  证据足够时返回稳定 JSON 业务结果，证据不足返回 None；明确 refuted 仍是可复算结果，不等于 None。
  只读取传入且保留的证据，不从全量包/外部文件/缓存补答案，不联网或调用模型。
  业务返回中不带变化的时间戳、耗时、随机 ID、证据条数；执行元数据另存。
  如果正式判定还需要额外固定上下文，先列出来与 A 对齐，不暗中依赖本机状态。

C-2 固定输入、预期输出和运行方法（随 C-1 一起返回）。
  至少：结论成立、结论被反驳、证据不足三例。每例给输入文件、claim ID、规则版本、预期结果和实际结果。
  同输入双跑应得到同一业务结果；说明每例真正必需的 evidence.ref。
  扩展回传来源值不一致、定位不存在、不支持规则和其他异常场景，明确原因。
  A 据此检验最小化；不能只给函数名或截图而缺可运行文件。

C-3 正式核验记录（R2）。
  按 claim 给正式状态、原因、引用证据、规则与检查版本、独立 verifier 输出/版本、双跑记录、新鲜度规则及结果。
  附输入包摘要和实际核验覆盖范围；独立 verifier 不得仅复制主 checker 的状态。
  明确哪些字段由共享模型承载、哪些是待定版辅助记录；不要自行修改冻结字段。
  同步给 B 供 L/R/D/F 评分，A 用副本确认删减后仍保留正式复核所需输入。

C-4 实测成本、代码清单和验收结果（R2/R3）。
  正式复算、双跑、独立核验、入账、失败/重试和实际人工处理，记录清楚边界及是否已被另一项包含。
  附 C 自己的改动文件、依赖、命令、输出和测试记录。M6/M7/M8/M13 等分别报告，未覆盖的明确列出。
  账本与闸门最终交付还需按 C_HANDOFF.txt 完成；不要求为了先交 replay 而提前宣称全部完成。

五、统一回传包装方式

建议分别命名 B_return_R1_<日期或版本>.zip、C_return_R1_<日期或版本>.zip；后续批次增加 R2/R3 标记，避免混淆。
建议结构（文件名可调整，但说明中的路径必须与实际文件一致）：
  RETURN_NOTE.txt             填写 return_templates/RETURN_NOTE_TEMPLATE.txt
  RETURN_MANIFEST.json        填写本角色的 B_RETURN_TEMPLATE.json 或 C_RETURN_TEMPLATE.json
  changed_files/             修改/新增的源文件，内部保留原仓库相对目录
  interfaces/                规则、字段映射、接口版本、必要的变更请求
  cases/                     固定输入、预期输出及结果说明
  results/                   实际运行输出与模块指标
  measurements/              原始操作实测记录；按成本模板说明填写
  verification/              运行命令、测试结果、依赖说明与可重复的验证步骤

若使用补丁，注明基准版本并附应用与验证方式；本轮没有 Git 提交号也可以按文件摘要回传。
改动包必须带齐新入口需要的文件和依赖；接收方不应依赖交付者电脑上未附带的模块、文件或环境变量才能运行。
填写 JSON 模板后将 template_only 改为 false；回传说明 completion_status 可标 ready_for_integration、partial 或 blocked，并解释未完成项；成本记录 measurement_status 可标 measured 或 incomplete。以上是材料状态，不代表业务验收通过。
不要回传 .env、密钥、虚拟环境、缓存或代理配置；实际模型配置由接收方本地管理。
时间带时区，文件使用 UTF-8 和可搬走的相对路径。失败、缺测、未完成项有专门位置，不从结果文件里删去。
已知不发生的调用/人工可实测记 0，未测填 null 并写原因；不要把模板当数据直接上交。
无需为了回传重新付费跑已有 A 数据。新增真实调用由执行者记录其用途、次数和实际用量。

六、A 收到后的处理与回执

A 按 RECEIVING_CHECKLIST.txt 对照版本、文件归属、输入/输出和成本边界，先小样例接入再扩到批量。
B/C 的代码问题由对应负责人处理；A 修改自己的采集、证据打包和成本统计。冻结接口由接口负责人统一定版。
A 回给 B/C：已接收的批次、已通过的联调项、未通过的复现信息、生成的新包/报告位置、仍待谁补的内容。
“接收通过”只表示这批材料可用于联调；最终项目与 M10 是否通过仍看完整测量和全队验收报告。
